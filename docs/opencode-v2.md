# Интеграция OpenCode v1/v2

По умолчанию приложение использует v1. Поддержка v2 проверяется на OpenCode
2.3.0. Выбор версии API независим от режима `direct`/`podman`.

## Архитектура

`backends/contracts.py` определяет `OpenCodeBackend`, общие ошибки и формат
истории. `backends/v1.py` и `backends/v2.py` реализуют контракт, `factory.py`
выбирает адаптер, а `http.py` отвечает за HTTP и SSE. `opencode_client.py`
содержит управление процессами, leases и простой. Импорт `OpenCodeClient`
сохранён как совместимый псевдоним клиента v1.

`backends/creation.py` сохраняет восстановление создания сессий из основной
ветки: оба адаптера атомарно записывают `metadata.shodanCreationKey` и ищут его
после потери ответа. Повтор POST разрешён только при доказанном отсутствии
отправки. Фасад берёт новый lease для каждого чтения или создания, освобождает
его на время backoff и поддерживает отмену ожидания.

История имеет общий формат `info`/`parts`, события — `payload` с явно указанным
владельцем сессии. В v2 преобразуются модели, права, формы и очередь входящих
сообщений. Результат определяется по серверному состоянию и истории; пропуск
события при переподключении SSE не завершает задание и не отправляет prompt заново.

Prompt использует сохранённый `message_id`. После потери подтверждения адаптер
сверяет историю и inbox. Если результат неизвестен, задание сохраняет слот и
`submission_uncertain`, проверяя тот же ID. Перезапуск шлюза не отправляет такой
prompt повторно. Отмена также ждёт подтверждения исходного запроса, затем
удаляет ожидающие входящие сообщения и проверяет остановку выполнения. При
длительной неопределённости восстановите доступ к исходному серверу и проверьте
его состояние: отсутствие сообщения в одном снимке не доказывает отказ.

## Настройки прямого запуска v2

Установите CLI отдельно от v1, например в выделенный каталог сервиса:

```sh
npm install --prefix /opt/valeria/opencode-v2 --no-audit --no-fund @opencode/cli@2.3.0
```

Пример `.env`:

```dotenv
OPENCODE_API_VERSION=v2
OPENCODE_BIN=/opt/valeria/opencode-v2/node_modules/.bin/opencode
OPENCODE_V2_STATE_ROOT=./data/opencode-v2
OPENCODE_V2_CONFIG_DIR=/etc/valeria/opencode-v2
OPENCODE_PASSWORD=replace-with-a-private-password
```

`OPENCODE_V2_CONFIG_DIR` должен содержать `opencode.jsonc`; основа —
[`docker/opencode-v2.jsonc`](../docker/opencode-v2.jsonc). Настройте провайдер,
модель и MCP своего окружения, используя ссылки на переменные окружения для
секретов. Сервер поддерживает многие конфигурации v1, но плагины должны иметь
реализацию API v2.

В v2 username Basic auth фиксирован: `opencode`. `OPENCODE_PASSWORD` имеет
приоритет над совместимым `OPENCODE_SERVER_PASSWORD`. Username v1 сохраняет
прежнее поведение.

Менеджер создаёт отдельные XDG data/state/cache/config каждого workspace внутри
`OPENCODE_V2_STATE_ROOT`. Глобальные настройки и учётные данные v1 автоматически
не копируются. Старые `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR` и
`OPENCODE_CONFIG_CONTENT` заменяются явной настройкой v2. Проектные
`opencode.json(c)` и `.opencode/` по-прежнему загружает OpenCode: проверьте их
перед запуском. Каталоги должны быть доступны сервисному пользователю.

## Переход существующей установки

1. Завершите или отмените все задания, включая ожидающие ответа и разрешения.
2. Остановите сервис и все его OpenCode/MCP-процессы. Сделайте резервную копию
   SQLite и текущих каталогов состояния.
3. **Со старой конфигурацией и старым бинарником** выполните:

   ```sh
   opencode-web backend-switch --to v2
   ```

   Для Docker, до изменения `.env` и сборки нового образа:

   ```sh
   docker compose run --rm --no-deps web opencode-web backend-switch --to v2
   ```

   Команда сохранит истории чатов и тасок в SQLite и подготовит переход.
   Консультации уже хранят вопросы и итоговые ответы в SQLite. Незавершённые
   задания, занятые runtime-порты, работающий сервис или ошибка чтения истории
   блокируют подготовку. Активная версия пока не меняется.
4. Настройте v2 и запустите сервис. Он атомарно применит подготовленный переход.
   Старые диалоги сохранятся для чтения; новые создаются в выбранной версии.
   Неподготовленная смена версии при наличии истории блокируется до запуска workers.

Если после подготовки снова запустить старую версию приложения, подготовка
сбрасывается: истории необходимо сохранить заново. Для отката остановите сервис
v2, выполните `backend-switch --to v1` с текущими настройками, затем верните
настройки и бинарник v1. Архивные диалоги остаются доступны для чтения; для новой
работы создавайте новый диалог.

## Docker и Podman

Оба Dockerfile принимают `OPENCODE_API_VERSION=v1|v2`, `OPENCODE_VERSION=1.18.25`
и `OPENCODE_V2_VERSION=2.3.0`. Compose передаёт их из `.env`. Для v1 используется
пакет `opencode-ai`, для v2 — `@opencode/cli`. После смены версии пересоберите
основной образ. Требования основной сборки к локальному `opencode/config`
сохраняются.

Для Compose конфигурацию v2 можно хранить в `./data/opencode-v2-config/`:
существующий mount `./data:/app/data` делает её доступной в контейнере.
В `.env` задайте `OPENCODE_V2_CONFIG_DIR=/app/data/opencode-v2-config`
и `OPENCODE_V2_STATE_ROOT=/app/data/opencode-v2`. Поместите туда
`opencode.jsonc` и настройте провайдера до запуска.

Изолированный worker v2:

```sh
podman build -f docker/Containerfile.opencode \
  --build-arg OPENCODE_API_VERSION=v2 \
  --build-arg OPENCODE_V2_VERSION=2.3.0 \
  -t localhost/valeria-opencode:2.3.0 .
```

Задайте `PODMAN_IMAGE=localhost/valeria-opencode:2.3.0`, отдельный
`PODMAN_CONFIG_DIR` с конфигурацией v2 и переменные провайдера в
`PODMAN_FORWARD_ENV`. Homes v2 находятся в `PODMAN_STATE_ROOT/v2/`, homes v1
сохраняют прежние пути. Каждый worker получает отдельный пароль через окружение,
без значения в аргументах процесса.

## Проверки

```sh
pytest -q tests/test_backend_v2.py tests/test_backend_switch.py \
  tests/test_backend_runtime_config.py tests/test_submission_reconciliation.py
```

Настоящие серверы и локальный тестовый провайдер, без платной модели:

```sh
OPENCODE_V1_TEST_BIN=/path/to/v1/opencode \
OPENCODE_V2_TEST_BIN=/path/to/v2/opencode \
pytest -q tests/test_backend_live.py
```

Проверяются ответы модели, история, события, каталог моделей, формы v2,
таска plan/build и консультация. `OPENCODE_TEST_DCP=1` дополнительно подключает
локальный DCP из `mcp/opencode-dcp-local` к v2; нужны установленные зависимости
плагина. Это проверяет загрузку и обычный запрос, но не заменяет наблюдение
за компрессией длинной сессии. DCP v2 имеет собственные ограничения режима `ask`.

Вопросы поддерживают строку, множественный выбор, boolean, number и integer;
метки вариантов переводятся в значения формы. Условные и external-поля
не поддерживаются текущим интерфейсом вопросов: адаптер сообщает ошибку,
сохраняя видимость проблемы вместо скрытия ожидающего взаимодействия.

Источники контракта: [официальный API](https://opencode.ai/docs/api),
[@opencode/client 2.3.0](https://www.npmjs.com/package/@opencode/client/v/2.3.0),
[руководство миграции](https://opencode.ai/docs/migrate-v1/).
