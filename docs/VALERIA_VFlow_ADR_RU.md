# VFlow — ADR-001…004

**Статус:** принято 20.11.2026
**Контекст:** реализация VFlow внутри существующего VALERIA-приложения.

## ADR-001. Границы модуля и именование

**Решение.** VFlow живёт в пакете `src/opencode_web/vflow/`. Для сущностей VFlow используется префикс `vflow_`, чтобы не смешивать их с существующей цепочкой задач (`task_successors`, `queue_jobs.pipeline_json`). Публичные HTTP-маршруты сохраняют терминологию спецификации: `/api/pipelines`, `/api/pipeline-runs`, `/api/admin/vflow/*`.

**Причина.** В коде уже есть «pipeline» в смысле автоматической цепочки дочерних задач. Если назвать таблицы `pipeline_*`, при сопровождении легко перепутать две разные модели. Префикс `vflow_` делает границу явной.

**Следствия.**
- `vflow_definitions`, `vflow_versions`, `vflow_runs`, `vflow_points`, `vflow_fork_instances`, `vflow_merge_arrivals`, `vflow_task_links`, `vflow_events`, `vflow_audit_events`, `vflow_outbox`.
- Старый `pipeline_json` не переименовывается и не переиспользуется.
- Новые поля корреляции дочерних задач: `vflow_run_id`, `vflow_point_id`, `origin_node_id` (или эквивалентная связь через `vflow_task_links`).

## ADR-002. Task Gateway и атомарность

**Решение.** VFlow использует существующую общую очередь `queue_jobs`, но через отдельный `ValeriaTaskGateway`. Постановка задачи выполняется в транзакции `Database.transaction()` (`BEGIN IMMEDIATE`): создаются `vflow_task_links`, `queue_jobs` и `chats`; при неопределённом результате enqueue используется `vflow_outbox` и reconciliation. Для VFlow-задач авто-порождение `task_successors` отключено.

**Причина.** VFlow не должен запускать OpenCode напрямую и не должен создавать второй механизм очереди. При этом существующий `create_task_job()` рассчитан на пользовательский запуск публичной задачи и автоматически создаёт детей.

**Следствия.**
- Новый gateway-метод проверяет задачу по опубликованной версии пайплайна (делегирование), а не только по `tasks.is_published`.
- Дочерний `queue_jobs` создаётся с пустым/контролируемым `pipeline_json`, чтобы `_enqueue_pipeline_children()` не сработал.
- Ожидание задачи не держит транзакцию и слот OpenCode; runtime опрашивает БД и просыпается по событию `job.updated`.
- Для неопределённого enqueue сначала фиксируется outbox-намерение, затем выполняется постановка; повторный проход ищет уже созданную задачу по `enqueue_key`.

## ADR-003. Роли, аудитория и делегирование

**Решение.**
- Пользовательская вкладка «Пайплайны» доступна `user`, `admin` и `tasks_only` (если включён доступ).
- Аудитория версии: `all` или `selected` (список пользователей), по аналогии с задачами.
- Администратор публикует версию с явным списком разрешённых Task ID. Это делегирование даёт VFlow право поставить задачу от имени инициатора, даже если задача не видна пользователю в каталоге.
- `public_result` в MVP не показывается; API отдаёт только безопасные статусы и агрегированный прогресс.
- Чужие Run всегда дают `404`, а не `403`, чтобы не раскрывать существование объекта.

**Следствия.**
- Серверные проверки: публикация, audience, ownership, workspace, разрешённые Task ID, лимиты.
- В пользовательском API нет `node_id`, `task_id`, `fork_stack`, промежуточного JSON и prompt-ов.
- Тестовый Run администратора использует его workspace; если workspace не назначен, запуск отклоняется с понятной ошибкой.

## ADR-004. Версии IR, Registry и совместимость

**Решение.** IR версионируется (`ir_version=1`). Каждый узел хранит `type` и `type_version`. Registry — code-only, с явными `NodeSpec`/`NodeHandler`. Публикация фиксирует `required_handlers_json` и `graph_hash`; активный Run не переключается на новую версию handler-а. Новый тип блока добавляется только поставкой кода и перезапуском/деплоем.

**Следствия.**
- Неизвестный `type` или `type_version` при старте Run — ошибка, а не «мягкая» деградация.
- Старые handler-версии должны оставаться доступными, пока существуют незавершённые Run.
- UI получает типы и схемы из Registry, а не из захардкоженного списка.
- Пользовательский плагин/JS/Python/SQL невозможен по дизайну.
