1. Назначение

1.1. Цель

Реализовать внутри существующего веб-приложения VALERIA дополнительный модуль VFlow, предназначенный для создания, публикации, запуска и мониторинга многошаговых пайплайнов, состоящих из готовых задач VALERIA и операторов управления потоком данных. Модуль должен отображаться как отдельная вкладка, интегрироваться с существующими аккаунтами, очередью задач, механизмом доступа, БД, журналированием и жизненным циклом приложения.

VFlow — персистентная интерпретируемая графовая state machine с множественными точками выполнения. Граф хранится в БД. В каждый момент у одного запуска пайплайна может быть несколько независимых точек выполнения, каждая со своей текущей вершиной, JSON-данными, состоянием ожидания и контекстом разветвлений.

Операции VFlow не заменяют исполнитель задач VALERIA: узел Task ставит существующую задачу VALERIA в очередь и ожидает её завершения. Остальные базовые операторы исполняются непосредственно движком VFlow.

1.2. Основные инварианты

  1. Пайплайн — отдельная сущность, не разновидность таски VALERIA.
  2. Определение пайплайна и экземпляр его запуска — разные сущности.
  3. Граф описывает переходы между узлами и хранится в базе данных, а не только в браузере или файле.
  4. Один запуск может содержать несколько активных точек выполнения. Не существует единственного глобального current_node.
  5. Каждая точка переносит JSON-значение и собственный контекст исполнения.
  6. Task создаёт обычный запуск существующей таски VALERIA, сохраняет его ID и ожидает терминального состояния; не выполняет агента самостоятельно.
  7. Transform меняет передаваемое JSON-значение; If только выбирает переход и не изменяет JSON.
  8. Fork N последовательно создаёт N дочерних точек выполнения, передавая каждой независимую копию входного JSON; затем дочерние точки могут выполняться конкурентно.
  9. Merge — строгий барьер: ожидает все N веток соответствующего экземпляра Fork, упорядочивает данные по индексу ветки, поглощает дочерние точки и создаёт ровно одну продолжающую точку.
  10. Нет режима first success, частичного слияния или автоматического обхода неготовых веток в базовой реализации.
  11. На старте поддерживаются четыре системных оператора: Transform, Fork N, Merge, If. Все остальные исполняемые узлы графа — ссылки на задачи, заранее созданные в VALERIA.
  12. Дальнейшие системные типы блоков могут быть добавлены только автором/разработчиком через исходный код и развёртывание VALERIA. Конечные пользователи и администраторы не устанавливают собственный код блоков через UI.
  13. Только администратор создаёт, редактирует, проверяет и публикует пайплайны; пользователи в отдельной вкладке могут запускать доступные опубликованные пайплайны и отслеживать свои запуски, но не редактировать схемы.
  14. Опубликованный запуск привязан к неизменяемой версии графа. Редактирование или повторная публикация не меняют уже начатые запуски.
  15. Все критические изменения состояния сохраняются транзакционно; рестарт VALERIA не должен терять принятые задания или точки выполнения.
  16. Системные блоки, входные данные, условия и тексты задач не должны создавать произвольную возможность выполнения Python/JavaScript/SQL от имени пользователя.

1.3. Не входит в первоначальный объём

  • Визуальное создание определений задач VALERIA вместо существующего раздела настроек задач.
  • Установка пользовательских плагинов, скриптов, Python-модулей или расширений непосредственно из интерфейса.
  • Планировщик по cron, webhook-trigger, внешние события как штатные способы старта; v1 запускается вручную или через авторизованный HTTP API. Такие способы можно добавить позднее разработчиком как расширения.
  • Распределённый кластер исполнителей с отдельным брокером сообщений как обязательное требование MVP.
  • Произвольный язык общего назначения со стеком функций, классами и системными вызовами.
  • Редактирование опубликованной версии на месте или изменение графа активного запуска.

2. Основание интеграции с существующей VALERIA

По публичному README VALERIA на момент подготовки спецификации: приложение — многопользовательский интерфейс на Python 3.12+, FastAPI/Jinja2, использующий SQLite, общую очередь задач и OpenCode v1/v2; администратор создаёт и публикует определения Task; пользователи запускают опубликованные задачи в своих workspace; задания сохраняются при перезапуске; запросы на создание защищены Idempotency-Key; пользователи видят только безопасную информацию о запусках тасок. Существует тип аккаунта tasks_only. Это известные требования совместимости, но не гарантия конкретных внутренних методов и таблиц. При разработке нужно адаптировать интеграционные интерфейсы к фактическому коду репозитория.

Повторно использовать, а не дублировать: авторизацию и сессии, роли, доступные аудитории задач, проверку workspace, механизм постановки задач в FIFO/общую очередь, механизм идемпотентного принятия запуска, получение статусов задач, административный аудит, обработку рестарта и изоляцию OpenCode.

Добавить отдельно: модели и версии пайплайнов, графовый DSL/IR, реестр системных блоков, исполнение state machine, диспетчер точек, ожидания Task, барьеры Merge, пользовательский список пайплайнов и редактор администратора.

2.1. Обязательный внутренний интерфейс к существующей системе задач

class ValeriaTaskGateway(Protocol):
    async def get_task_definition(self, task_id: str) -> TaskDefinition: ...
    async def authorize_pipeline_task(self, user_id: str, pipeline_id: str, task_id: str) -> None: ...
    async def enqueue_task(
        self,
        *,
        user_id: str,
        task_id: str,
        task_snapshot: dict,
        workspace_id: str,
        additional_text: str,
        idempotency_key: str,
        origin: dict,
    ) -> str: ...
    async def get_task_state(self, task_run_id: str) -> TaskState: ...
    async def get_final_task_answer_internal(self, task_run_id: str) -> str | None: ...
    async def request_task_cancel(self, task_run_id: str) -> None: ...

Это контракт-адаптер, а не утверждение, что методы уже существуют. Если существующая очередь не отдаёт VFlow финальный результат таски, необходимо добавить закрытый внутренний метод извлечения итогового ответа. Этот метод не должен расширять права обычных пользователей на чтение скрытых промптов, reasoning, сообщений инструментов или технических ошибок.

Если существующий диспетчер задач работает в той же SQLite, предпочтительна атомарная транзакция, связывающая точку и задачу. Иначе требуется outbox/idempotency/reconciliation. Нельзя запускать OpenCode напрямую из Task-узла, минуя очередь.

3. Сущности и терминология

Термин Определение
Pipeline Definition Логическая именованная сущность пайплайна, его владелец/администратор, описание и аудитория.
Pipeline Version Неизменяемая после публикации версия графа, DSL/IR и требуемых типов блоков.
Pipeline Run Конкретный запуск конкретной опубликованной версии определённым пользователем с входным JSON.
Node Вершина графа: системный оператор или ссылка на готовую задачу VALERIA.
Edge Направленный переход от выходного порта одной вершины к входу другой.
Execution Point / Token Персистентная единица исполнения: позиция в графе + JSON + состояние + контекст Fork/Merge.
Point Transition Один успешно сохранённый переход одной точки через узел либо её перевод в состояние ожидания.
Fork Instance Одна конкретная активация узла Fork в данном Run, со своей группой N веток.
Branch Index Стабильный индекс ветки от 0 до N-1 внутри Fork Instance.
Fork Stack Стек контекстов активных Fork, позволяющий корректно обрабатывать вложенные развилки.
Merge Arrival Персистентная запись факта, что ветка нужного Fork достигла связанного Merge.
Node Handler Разработческий обработчик одного типа системного блока, зарегистрированный в коде VALERIA.
Registry Реестр доступных системных типов блоков, их версий, форм параметров, портов и обработчиков.
IR Каноническое типизированное промежуточное представление графа, хранимое в БД и исполняемое интерпретатором.

3.1. Пример нескольких точек

Pipeline Run #9001 — RUNNING — Graph Version #12
    Point #51: node=review_task,  state=WAITING_TASK,  job=task-run-710
    Point #52: node=security,     state=READY,         data={...}
    Point #53: node=merge_1,     state=WAITING_MERGE, merge=fork-411

Все точки принадлежат одному запуску, но находятся на разных вершинах. Ожидание одной таски не мешает другим точкам продвигаться по графу. Точка на Merge не занимает worker OpenCode.

4. Роли, полномочия и аудитории

4.1. Роль «пользователь»

В отдельной вкладке «Пайплайны» / Pipelines обычный пользователь и пользователь tasks_only, если ему выдан доступ к модулю, могут:

  • видеть только опубликованные и доступные по аудитории пайплайны;
  • видеть публичное название, описание, версию, требования к входным данным, собственные запуски и их безопасные статусы;
  • вводить/редактировать разрешённый входной JSON в форме, генерируемой по схеме, либо в JSON-редакторе, если это разрешил администратор;
  • запускать пайплайн; просматривать историю своих запусков; обновлять статус;
  • по отдельно предоставленному праву pipeline.cancel_own запрашивать отмену своего запуска;
  • получать только специально разрешённый публичный результат, если администратор включил такую выдачу; по умолчанию — статусы без внутренних результатов.

Не могут: открывать административный редактор, видеть DSL/структуру графа, список скрытых задач, внутренние JSON промежуточных узлов, скрытые промпты, логи OpenCode, результаты других пользователей, создавать или публиковать пайплайны, добавлять типы блоков, выполнять произвольные скрипты.

4.2. Роль «администратор»

В отдельной вкладке «Редактор пайплайнов» / Pipeline Editor администратор может:

  • создавать, копировать, архивировать определения пайплайнов;
  • собирать граф, редактировать параметры узлов и связей, переключаться между графом и VFlow-кодом;
  • выбирать существующие задачи из каталога VALERIA;
  • проверять синтаксис, типы, парность Fork/Merge, доступность задач, безопасность и ограничения;
  • сохранять черновики, публиковать новую неизменяемую версию, откатывать активную публикацию на прежнюю версию;
  • настраивать аудитории, входную JSON Schema, ограничения, политику видимости результатов;
  • запускать тестовые/обычные экземпляры и наблюдать все доступные администратору Run, точки, переходы и ошибки;
  • запрашивать отмену Run, читать диагностические события и данные по полномочиям администратора.

Администратор не добавляет новые типы системных блоков через интерфейс: это делает только разработчик через код и деплой. Администратор выбирает из уже зарегистрированных видов операторов.

4.3. Разработчик VALERIA

Разработчик — не отдельная веб-роль. Это лицо, имеющее доступ к исходному коду, тестам и развёртыванию. Только он может добавить новый Node Handler, новую схему параметров и версию блока в реестр. При этом существующие администраторы увидят новый системный блок в палитре после релиза. Нельзя трактовать владение админ-аккаунтом как право выполнить код расширения на сервере.

4.4. Политика доступа к вложенным задачам

Публикация пайплайна, содержащего задачу, должна явно определять делегированное право выполнить эту задачу именно в контексте указанного пайплайна. Пользователь не получает права напрямую запустить скрытую задачу или прочитать её настройки. Сервер проверяет, что текущая версия опубликована для пользователя, а задача разрешена этой версии. Все дочерние Task Run исполняются с реальным user_id инициатора и его разрешённым workspace; обход workspace-политик недопустим. Факт делегирования виден в административном аудите.

Альтернатива «все задачи должны быть доступны пользователю напрямую» более строгая, но ограничивает полезность составных пайплайнов. В этой спецификации зафиксировано делегирование на уровне опубликованной версии как целевое поведение.

5. Интерфейс: дополнительные вкладки в существующей VALERIA

5.1. Навигация

Новые пункты в текущем меню VALERIA:

  • «Пайплайны» — пользовательская вкладка: каталог и запуски.
  • «Редактор пайплайнов» — административная вкладка, скрытая для не-администраторов и закрытая серверной проверкой прав.

Модуль встроен в существующий сайт, с общей сессией, профилем и стилями, не требует отдельной авторизации и не становится отдельным сервисом без необходимости. Маршруты примера: /pipelines, /admin/pipelines, /admin/pipelines/{id}/editor.

5.2. Пользовательская вкладка «Пайплайны»

Содержит каталог карточек: название, описание, дата публикации, статус доступности, версию, краткие правила входных данных и кнопку «Запустить». Нажатие открывает форму параметров. Форма генерируется по публичной input_schema с поддержкой обязательных полей, типов, перечислений, размеров и подсказок; валидируется браузером для UX и повторно сервером для безопасности.

После запуска UI показывает run_id, текущий статус и прогресс: сколько Task Run ожидают в очереди/выполняются, сколько активных точек, сколько точек ждут Merge (в безопасном агрегированном виде). В пользовательском интерфейсе нет схемы графа, названий скрытых узлов и результатов внутренних тасок. История показывает только собственные запуски с фильтрами и пагинацией. Отмена доступна, если включена в политику публикации.

Публикация результата: по умолчанию только статус (status_only). Если у версии выставлен public_result, администратор должен определить отдельную безопасную трансформацию/схему экспортируемых данных; выдача «всего внутреннего JSON» запрещена по умолчанию.

Левая панель: отдельная группа «Системные блоки» — ровно четыре оператора; другая группа — реальные определения задач VALERIA (название, категория, ID, доступность). Кнопка «Создать таску» может вести в существующий административный раздел, не создаёт таску через VFlow. Поиск по блокам и задачам. После добавления разработчиком нового системного блока он автоматически появляется в группе системных операторов по метаданным Registry.

Центральная область: масштабирование, панорамирование, перетаскивание блоков, перемещение узлов, создание/удаление рёбер, отображение портов (true, false, branch[0..N-1]), start/end как визуальные терминалы, автокомпоновка, миникарта по желанию. Все узлы имеют стабильные ID; положение на Canvas хранится в версии графа. Ошибочные соединения подсвечиваются ещё до публикации.

Правая панель: динамическая форма настроек по JSON Schema из Registry. Для Task — выбор task_id, JSONPath входа, сериализация входа, формат ответа, retries/timeout в пределах политики; для If — JSONPath, оператор сравнения, типизированный литерал, поведение отсутствующего поля; для Fork — N и парный Merge; для Merge — ожидаемый Fork (только all); для Transform — список безопасных операций преобразования. Инспектор показывает описание и предпросмотр результата на тестовом JSON без запуска агента.

Нижняя панель: диагностика компилятора, журнал админ-запуска, последовательность событий и активные точки по ID. При выборе конкретного запуска подсветка на графе имеет мультисостояние: на одной вершине может быть 0, 1 или несколько точек; нельзя рисовать одну «единственную бегущую стрелку».

Верхняя панель: имя, версия, признак черновика, доступность, undo/redo, «Сохранить черновик», «Проверить», «Опубликовать», «Запустить», вкладки «Граф», «Код», «Запуски».

5.4. Два способа редактирования

  • Графический редактор редактирует канонический Graph IR.
  • Текстовый редактор VFlow парсит DSL в тот же Graph IR.
  • Переключение граф → код генерирует канонический DSL; код → граф возможно только после синтаксической и семантической проверки.
  • Семантика должна совпадать в обоих представлениях; оформление текста, пробелы и комментарии при round-trip могут быть нормализованы.
  • Чтобы не потерять пользовательский текст при неуспешном парсинге, исходник сохраняется в локальном черновике редактора до исправления ошибок; предыдущий валидный IR не перезаписывается.
  • Долгоживущий опубликованный IR нельзя пересобирать из текущей версии Registry с изменением поведения.

5.5. Валидация и публикация

Кнопка «Сохранить» сохраняет черновик даже с неполным графом, но показывает ошибки. «Опубликовать» разрешено только при успешной полной валидации. Публикация атомарно фиксирует новую неизменяемую версию и переставляет указатель published_version_id. Для старых Run сохраняется прежняя версия. Снятие с публикации запрещает новые запуски, но не отменяет текущие.

6. Каноническая модель графа и данных

6.1. Граф

Граф — ориентированный набор nodes и edges, хранимый в SQLite как версионированный JSON IR. UI-позиции (x, y) не влияют на исполнение. Узлы идентифицируются стабильным node_id в пределах версии; связи содержат source_node, source_port, target_node. Терминалы start и end являются служебными маркерами редактора/компилятора, а не устанавливаемыми типами блока. Запуск начинается с единственного стартового перехода.

Пример фрагмента IR:

{
  "ir_version": 1,
  "workflow": "review_changes",
  "entry": "prepare",
  "nodes": [
    {"id": "prepare", "type": "core.transform", "type_version": "1.0", "config": {"operations": []}, "ui": {"x": 80, "y": 120}},
    {"id": "split", "type": "core.fork", "type_version": "1.0", "config": {"count": 3, "join_node_id": "joined"}, "ui": {"x": 330, "y": 120}},
    {"id": "review", "type": "valeria.task", "type_version": "1.0", "config": {"task_id": "code.review"}},
    {"id": "joined", "type": "core.merge", "type_version": "1.0", "config": {"fork_node_id": "split"}}
  ],
  "edges": [
    {"source": "prepare", "source_port": "out", "target": "split"},
    {"source": "split", "source_port": "branch[0]", "target": "review"},
    {"source": "review", "source_port": "out", "target": "joined"}
  ]
}

Это фрагмент, а не завершённый публикуемый граф (не все ветки имеют маршрут). Порядок элементов JSON nodes и edges не является порядком исполнения. Порядок задаётся только переходами и состоянием точек.

6.2. Передаваемое JSON

  • Значение точки data — корректное JSON-значение: объект, массив, строка, число, boolean или null.
  • Все элементы сериализуются согласно JSON; Python-объекты, даты без преобразования, бинарные объекты, файловые дескрипторы и несериализуемые типы запрещены.
  • Входной Run и результаты узлов ограничены в размере (предложение по умолчанию: 1 МиБ на JSON-значение, администратор/разработчик может ужесточить).
  • Операторы используют семантику передачи значения, не ссылок на разделяемый mutable-объект. Fork дочерним точкам передаёт независимые логические копии.
  • У каждой точки есть отдельные служебные metadata (run_id, point_id, branch_index, fork_stack, attempts), которые по умолчанию не являются частью пользовательского data и не меняются в If.
  • Никакой узел не получает неявного права читать данные другого пользователя/Run.

6.3. Входы и выходы портов

Тип Вход Выходы Поведение
Task in out Ожидание VALERIA Task Run; создание новой точки не требуется.
Transform in out Синхронное преобразование JSON.
If in true, false Проверка условия и выбор ровно одного ребра.
Fork N in branch[i] для каждого i Создание N новых точек и поглощение входящей.
Merge in (несколько входящих рёбер) out Ожидание N зарегистрированных прибытий и одна продолжающая точка.

У Task, Transform, Merge — ровно один выход out (допускается переход на end). У If при публикации обязаны быть подключены оба логических выхода. Для Fork должен быть задан согласованный набор N маршрутов: либо все branch[0..N-1], либо одно ребро от сокращённого общего порта all, разворачиваемое в N одинаковых маршрутов. Нельзя смешивать эти режимы. Визуальный редактор может сокращать общий all до одной стрелки.

7. Семантика базовых узлов

7.1. Task: постановка задачи VALERIA и ожидание

Исходное состояние: точка READY на узле Task с входным JSON.

Первый проход:

  1. Движок валидирует привязанное task_id, разрешение запуска от имени пользователя/опубликованной версии и его workspace.
  2. Определяет вход для таски по input_path (по умолчанию $, то есть весь входной JSON).
  3. Сериализует выбранное значение в добавляемый текст задания VALERIA (рекомендуется JSON с инструкцией «данные сценария», не интерпретируемый как доверенные команды).
  4. Создаёт ровно один обычный Task Run в существующей общей очереди с детерминированным idempotency key вида vflow:{run_id}:{point_id}:{visit_seq}:{attempt}.
  5. Сохраняет task_run_id, идентификатор попытки, время очереди/ожидания, переводит точку в WAITING_TASK и освобождает слот диспетчера VFlow.
  6. Дальнейшее прохождение через узел не создаёт новую таску, пока соответствующая попытка не получила подтверждённый терминальный статус.

Ожидание: служебный диспетчер получает события изменения статуса Task Run, если такой интерфейс доступен; при его отсутствии применяет периодический опрос по task_run_id с backoff. Опрос не занимает слот OpenCode. Временные сетевые ошибки чтения сохраняют WAITING_TASK, фиксируются и повторяются по политике, не создавая новую таску.

Успех: после подтверждённого COMPLETED движок читает только финальный ответ из внутреннего доверенного API задач, формирует новый JSON по контракту результата и переводит ту же точку к следующей вершине. Если результат недоступен, применяется result_mode=none либо зафиксированная ошибка; нельзя тайно подставлять пустой JSON, если дальнейшие узлы ожидают ответ.

Ошибка: подтверждённые FAILED или CANCELLED приводят к ошибке пайплайна по умолчанию. Опциональные автоматические повторы Task допускаются лишь при явной админ-настройке и понимании неидемпотентности действий агента; каждая повторная попытка — новый Task Run с новым attempt, но не повтор из-за сбоя HTTP.

Стандартный выход Task (result_mode=auto):

{
  "input": {"repository": "example/repo", "pr": 24},
  "task": {
    "task_id": "code.review",
    "run_id": "task-run-701",
    "status": "completed",
    "output": {
      "text": "{\"ok\":true,\"issues\":[]}",
      "json": {"ok": true, "issues": []}
    }
  }
}

Поле input — JSON, переданный в Task до сериализации; task.output.text — строка финального ответа; task.output.json — JSON, если весь финальный ответ строго распарсился как JSON, иначе null при auto; при result_mode=strict_json невалидный JSON считается ошибкой узла. Вход не мутируется в объекте, отданном ранее; формируется новый JSON-конверт. Task не возвращает reasoning или сообщения инструментов. input_path может выбирать JSON-фрагмент для передачи агенту, но input сохраняет полный вход, чтобы Transform мог использовать предыдущий контекст.

Снимок конфигурации: при создании Pipeline Run следует зафиксировать разрешённые настройки всех использованных Task (prompt/model/mode/вариант/опции) в защищённом внутреннем снимке выполнения; новые изменения Task внутри VALERIA не должны менять уже запущенный Run. Для нового Run можно брать актуальные настройки Task после повторной проверки доступа. Реализация может опираться на существующие task snapshots, если они уже присутствуют в очереди; если нет — требуется адаптер.

Таймаут: контролирует выполнение/ожидание в определённой политике. Время нахождения во внешней очереди отдельно от таймаута OpenCode; не следует считать длительный FIFO автоматически зависшим Task. Превышение лимитов фиксируется и инициирует отмену только при наличии поддержки со стороны существующей очереди.

7.2. Transform: изменение JSON

Transform — локальный чистый детерминированный оператор. Он получает JSON, последовательно применяет список декларативных операций и передаёт новое значение через out. Не создаёт таску VALERIA и не имеет сетевых/файловых побочных эффектов.

Набор операций v1: set(path, value), copy(from, to), move(from, to), remove(path), select(path) (замена текущего корневого значения выбранным фрагментом), merge_object(path, object) (слияние JSON-объектов на один уровень), append(path, value) (к JSON-массиву), rename(from, to). В value допускаются литералы JSON и явный ссылочный операнд { "from_path": "$.field" }. Операции set/append/copy могут использовать этот операнд без eval.

Правила:

  • Пути используют ограниченное подмножество JSONPath: $, .field, ['field'], [index]. Wildcards, функции, фильтры с произвольными выражениями и выполнение кода запрещены в v1.
  • Операции исполняются в указанном порядке, над промежуточным JSON.
  • Нет неявного создания вложенных массивов и бесконтрольного расширения объектов. Администратор выбирает явную политику create_missing только для объектных ключей.
  • Ошибка пути, несовместимый тип, циклическая ссылка (не существует в JSON) или превышение размера данных приводит к детерминированной ошибке узла с кодом.
  • Использование JSONPath не должно вести к обращению к Python-атрибутам или прототипам JS; ключи JSON рассматриваются только как данные.

Пример конфигурации:

{
  "operations": [
    {"op": "copy", "from": "$.task.output.json.issues", "to": "$.review.issues"},
    {"op": "set", "path": "$.review.processed", "value": true},
    {"op": "remove", "path": "$.task.output.text"}
  ]
}

Предпросмотр в UI запускается локально/через безопасный серверный endpoint на тестовом JSON; отладочный ввод не создаёт Task Run.

7.3. If: ветвление по полю входного JSON

If проверяет указанное поле того JSON, который получил. Параметры: path, operator, value, missing. Разрешённые операции v1: eq, ne, gt, ge, lt, le, contains (массив/строка), in (значение в списке), exists, is_null. Для exists отсутствие поля всегда возвращает false и не считается ошибкой missing=error; для остальных операторов отсутствие обрабатывается согласно missing. Сравнение типизированное, без автоматического приведения строки "12" к числу 12; порядок gt/ge/lt/le допустим только для сравнимых типов. missing = error (по умолчанию), false либо true.

Семантика:

  1. Читает поле по ограниченному JSONPath.
  2. Вычисляет boolean с учётом operator и missing.
  3. Выбирает true либо false порт.
  4. Сохраняет исходный JSON битово-эквивалентным по значениям (допускается нормализация сериализации) и перемещает ту же точку к выбранному узлу.

If не создаёт вторую точку, не передаёт копии в обе стороны и не меняет пользовательские данные. У него оба порта должны быть привязаны к корректным маршрутам. Если обе ветки потом ведут в один обычный узел, это допустимый control-flow join без Merge, так как активна только одна ветка.

7.4. Fork N: N копий и N независимых точек

Fork получает JSON и целое N в допустимых границах (2 ≤ N ≤ configurable max, рекомендуемый начальный предел 32). Рядом задаётся join — ID парного Merge. N в v1 — админ-константа, а не вычисляемое выражение; поддержка динамического N возможна отдельным расширением.

Атомарный алгоритм:

  1. Интерпретатор начинает транзакцию БД, проверяя, что входная точка ещё не обработала этот конкретный вход в Fork.
  2. Создаёт один fork_instance с run_id, fork_node_id, join_node_id, expected_count=N, снимком входного JSON для последующего Merge и ссылкой на родительский контекст.
  3. Последовательно, с i=0 по N-1, создаёт N новых execution_points: branch_index=i, копия входного JSON, fork_stack = parent_stack + current_frame, стартовый successor определяется портом branch[i] или общим all.
  4. Помечает исходную точку FORKED/CONSUMED (в дальнейшем её нельзя запланировать).
  5. Коммитит всю транзакцию одновременно. Только после коммита дочерние точки доступны диспетчеру для независимой конкурентной обработки.

Таким образом последовательность создания дочерних точек не означает их последовательное выполнение. Если приложение упало на середине транзакции, после восстановления будет либо 0 новых точек, либо все N, но не частичный Fork. Повторный claim/вызов не может породить ещё N копий: уникальный ключ fork_instance фиксирует факт прохода.

Режимы маршрутизации:

  • split[0] -> task_a, split[1] -> task_b, ... — у каждой ветки собственный маршрут/таска.
  • split -> same_task — сокращение all: все N точек начинают с одного и того же узла, но это N отдельных посещений узла и N отдельных запусков таски, если следующий узел Task.

Служебные метаданные: каждая точка имеет индекс ветки и ID fork-instance. Они не добавляются в data автоматически; если таска должна знать индекс, в будущем может использоваться отдельная безопасная операция Transform «вставить metadata.branch_index в JSON», выполняемая с явным разрешением. В v1 при разных задачах используйте порты branch[i].

7.5. Merge: строгая синхронизация всех ветвей

Merge — узел с жёстким wait_all. Он должен быть привязан к определённому Fork в опубликованном графе. Каждый конкретный запуск этого Fork создаёт fork_instance_id; на Merge сравниваются не все точки в одном узле, а лишь точки с совпадающим run_id + fork_instance_id + merge_node_id.

Алгоритм прибытия ветки:

  1. Точка достигает Merge с верхним кадром fork_stack, указывающим именно на соответствующий Fork.
  2. В рамках транзакции движок вносит merge_arrival(fork_instance_id, branch_index, point_id, data_snapshot), используя уникальный ключ (fork_instance_id, branch_index).
  3. Помечает точку WAITING_MERGE/ARRIVED, больше не назначает её worker.
  4. Проверяет, прибыли ли все индексы от 0 до N-1, а не просто N произвольных событий.
  5. Если нет — завершает операцию ожиданием; если да — один worker под транзакционным compare-and-swap помечает fork_instance как MERGED и создаёт одну продолжающую точку после Merge.
  6. Созданная точка наследует родительский fork_stack без только что закрытого кадра; N дочерних точек помечаются CONSUMED. Результаты упорядочиваются по branch_index, а не по времени завершения.

Стандартный JSON после Merge:

{
  "source": {"repository": "example/repo", "pr": 24},
  "branches": [
    {"index": 0, "data": {"task": {"output": {"json": {"ok": true}}}}},
    {"index": 1, "data": {"task": {"output": {"json": {"tests": 112}}}}},
    {"index": 2, "data": {"task": {"output": {"json": {"warnings": 0}}}}}
  ]
}

source — входные данные непосредственно перед соответствующим Fork. branches[*].data — весь фактически пришедший JSON каждой ветки (пример сокращён). Нет автоматического интеллектуального объединения полей. При необходимости постобработка выполняется отдельным Transform.

Если ветка упала или завершилась без Merge: Merge не должен бесконечно ждать. При сбое любого обязательного потомка по стандартной политике весь Run становится FAILED с диагностикой недостигнутой ветки; при отмене Run — CANCELLED. Публикационный валидатор запрещает очевидные маршруты, минующие парный Merge. Временное отсутствие точки на Merge, пока таска ещё работает, — нормальное ожидание, не ошибка.

Нельзя: сливать точки разных запусков, разных активаций того же Fork в цикле, с разным верхним кадром fork_stack, либо с уже закрытым fork_instance. Дубликат прибытия не должен создавать повторную продолжающую точку.

7.6. Вложенные Fork/Merge

Корректная вложенность:

                   Fork A (N=2)
                 /              \
            Branch A0         Branch A1
                 |                 |
            Fork B (N=2)         Task C
             /      \              |
          Task D  Task E           |
             \      /              |
              Merge B              |
                 \                /
                       Merge A
                          |
                         End

fork_stack ветки A0 содержит кадр A; после Fork B — [A, B]; Merge B закрывает B, затем продолжающая точка с [A] приходит на Merge A. Прямая попытка попасть в Merge A с незакрытым B недопустима.

Правило структурированности: на один Fork — ровно один парный Merge; вложенные пары не пересекаются, внутренний Merge закрывается раньше внешнего. Каждый возможный маршрут дочерней ветки должен достигнуть своей пары (в том числе оба исхода If). Не допускаются связи, которые «выпрыгивают» из открытой области Fork, вход внутрь середины области снаружи, или повторно входят в тот же Merge после закрытия пары. Это проверяется на этапе публикации по графу/контекстам областей.

8. Текстовый язык VFlow

8.1. Общие принципы

Текстовый VFlow — декларативное описание того же графа, что и в визуальном редакторе. Сохраняется предложенный ранее стиль: workflow "name" { ... }, объявления узлов через step name = ..., связи через ->, выходы if.true / if.false и ветки fork[0]...fork[N-1]. Слово workflow описывает определение; step — узел; start/end — зарезервированные терминалы; порядок объявления step не влияет на порядок запуска.

В языке нет функций общего назначения и произвольного Python/JavaScript. Аргументы узлов — JSON-подобные литералы, типизированные поля и JSONPath. Вызов task.run означает отдельный запуск Task VALERIA через очередь, а не прямое выполнение модели.

8.2. Нормативный пример полного пайплайна

Ниже пример с тремя различными уже созданными задачами. Предполагается, что администратор предварительно создал в VALERIA задачи с указанными идентификаторами. join: combined явно связывает Fork и Merge. Ветки получают одинаковые данные, но разные Task ID.

workflow "review_changes" {
    version: 1
    input: json

    step context = task.run(
        task_id: "context.load",
        input: "$",
        result_mode: "strict_json"
    )

    step prepare = transform(
        operations: [
            {op: "copy", from: "$.task.output.json.repository", to: "$.context.repository"},
            {op: "copy", from: "$.task.output.json.pull_request", to: "$.context.pull_request"}
        ]
    )

    step split = fork(count: 3, join: combined)

    step review = task.run(task_id: "code.review", result_mode: "strict_json")
    step tests = task.run(task_id: "tests.run", result_mode: "strict_json")
    step security = task.run(task_id: "security.audit", result_mode: "strict_json")

    step combined = merge()

    step decision = if(
        path: "$.branches[0].data.task.output.json.ok",
        operator: "eq",
        value: true,
        missing: "error"
    )

    step accepted = task.run(task_id: "report.approved")
    step rejected = task.run(task_id: "report.rejected")

    start -> context -> prepare -> split
    split[0] -> review -> combined
    split[1] -> tests -> combined
    split[2] -> security -> combined
    combined -> decision
    decision.true -> accepted -> end
    decision.false -> rejected -> end
}

Важное уточнение: этот пример корректен в том смысле, что каждая ветка split обязательно достигает combined. If расположен после Merge. Если If находится внутри ветки Fork, обе его дуги должны привести к тому же Merge или к промежуточному пути, ведущему туда.

8.3. Пример Fork N с одной общей задачей

workflow "repeat_same_task_three_times" {
    version: 1
    input: json

    step split = fork(count: 3, join: joined)
    step worker = task.run(task_id: "analysis.generic")
    step joined = merge()

    start -> split
    split -> worker -> joined
    joined -> end
}

Компилятор разворачивает сокращение split -> worker в три логических маршрута; выполнение создаёт три разных Task Run, а не один общий. Их input одинаков по значению, если ни одна ветка не изменяла JSON до входа в Task.

8.4. Пример If с сохранением входного JSON

workflow "simple_if" {
    version: 1
    input: json

    step decision = if(path: "$.quality.score", operator: "ge", value: 80)
    step high = task.run(task_id: "quality.high")
    step low = task.run(task_id: "quality.low")

    start -> decision
    decision.true -> high -> end
    decision.false -> low -> end
}

decision не меняет $.quality.score и не оборачивает JSON в новую структуру. Проверка идёт строго по входному объекту. Только последующий Task произведёт свой результат-конверт.

8.5. Повторный проход (циклы)

В целом графовая state machine допускает циклы. Для v1 допускаются циклы вне открытых Fork/Merge-областей, например If -> Task -> Transform -> If, если они имеют достижимый выход и выполняются в пределах лимитов переходов. Повторный вход в Task создаёт новый Task Run с новым visit_seq. Внутренние циклы в ветках Fork разрешаются лишь если структурный валидатор доказывает отсутствие пересечения барьеров и все пути ветки имеют маршрут к Merge. При невозможности такого доказательства публикация отклоняется. Количество переходов/посещений ограничено настройками Run, чтобы ошибочный цикл не работал бесконечно.

8.6. Грамматика — концептуальный EBNF-профиль v1

workflow        = "workflow", string, "{", header*, statement*, "}" ;
header          = "version", ":", integer
                | "input", ":", "json" ;
statement       = node_decl | edge_chain ;
node_decl       = "step", identifier, "=", node_call ;
node_call       = qualified_name, "(", [ arg, { ",", arg } ], ")" ;
qualified_name  = identifier, { ".", identifier } ;
arg             = identifier, ":", value ;
value           = string | number | "true" | "false" | "null"
                | identifier | object | array ;
object          = "{", [ object_member, { ",", object_member } ], "}" ;
object_member   = identifier, ":", value ;
array           = "[", [ value, { ",", value } ], "]" ;
edge_chain      = endpoint, "->", endpoint, { "->", endpoint } ;
endpoint        = identifier, [ ".", identifier | "[", integer, "]" ]
                | "start" | "end" ;

Точное лексическое описание: UTF-8, identifier = [A-Za-z_][A-Za-z0-9_]*, string с JSON-экранированием, целые integer >= 0, числовые литералы в JSON-формате, комментарии // и # до конца строки. Пробелы/переводы строк — разделители, текст не чувствителен к отступам. value = identifier допускается только в явно типизированных местах, например join: combined; произвольный identifier как вычисляемая переменная запрещён. Дополнительные строки ; как разделитель MAY поддерживаться, но не обязательны.

if — зарезервированное имя обработчика, поэтому парсер должен поддерживать step decision = if(...) без конфликта с внутренним синтаксисом Python. Символ . после endpoint отделяет имя порта, тогда как в task.run — часть имени типа.

8.7. Семантическая компиляция

Порядок:

  1. Lexer/Parser: AST с позициями исходного текста.
  2. Name Resolution: проверка уникальных ID step, существование целей join, допустимые start/end.
  3. Registry Resolution: соответствие task.run, transform, fork, merge, if реальным типам/версиям Node Registry.
  4. Schema Validation: JSON Schema конфигураций, правильные типы аргументов и портов.
  5. Graph Validation: связи, достижимость, парность Fork/Merge, допустимость циклов и контекстов ветвей.
  6. Task Validation: существование задачных ID и их разрешённость для публикации данной аудитории.
  7. IR Build: канонический Graph IR, сохраняющий неизменяемые версии типов блоков.
  8. Publish: запись immutable version, хеша, кода/IR и актуализация указателя опубликованной версии.

Ошибки содержат code, message, line, column, node_id, edge_id при наличии. Редактор подсвечивает соответствующий участок кода или графа. Нельзя превращать синтаксически некорректный код в «частично работающий» опубликованный граф.

8.8. Правила валидации перед публикацией

Обязательные проверки:

  1. Единственный корректный start и достижимый end для каждого допустимого терминального маршрута.
  2. Все узлы/рёбра имеют уникальные ID, ссылки валидны, нет неявных пустых выходов.
  3. Нет бесхозных/недостижимых узлов (как минимум ошибка публикации, не предупреждение).
  4. If имеет ровно один путь по каждому true и false; никакой fan-out без Fork.
  5. Task и Transform имеют один маршрут out; безусловная раздвоенная дуга от любого обычного узла запрещена.
  6. Fork имеет валидный count, соответствующие порты и существующий единственный join.
  7. Каждый Fork закрывается только своим Merge; другие Fork не могут бесконтрольно делить Merge.
  8. Контексты вложенных Fork корректно стековые, не пересекаются и не обрываются переходами на end.
  9. Нет достижимого маршрута из дочерней ветви к end без достижения её Merge. Ветки с If проверяются по обоим возможным исходам.
  10. Циклы и обратные дуги не могут нарушать стековую дисциплину; ограничения на переходы установлены.
  11. Существуют необходимые задачи, их конфигурация валидна, доступно право запускать их через публикацию и workspace-политики.
  12. Каждая схема входа/выхода и операция преобразования укладывается в лимиты и разрешённый язык выражений.
  13. Все требуемые типы и версии обработчиков зарегистрированы; неизвестный или недоступный блок делает версию непубликуемой.
  14. Версия IR совместима с runtime; граф нельзя опубликовать, если сериализованный IR не может быть исполнен.

Ограничение доказуемости: произвольный циклический граф с данными и If в общем случае нельзя полностью проверить на завершение статически. Поэтому компилятор обеспечивает структурную корректность Fork/Merge, отклоняет сомнительные переходы, а runtime вводит бюджеты времени/переходов. Публикация не гарантирует, что бизнес-условия обязательно когда-либо позволят завершить цикл.

9. Execution Point: конечный автомат состояния одной точки

9.1. Поля точки

{
  "id": "point-203",
  "run_id": "run-9001",
  "node_id": "review",
  "status": "WAITING_TASK",
  "data": {"repository": "example/repo", "pr": 24},
  "visit_seq": 4,
  "attempt": 0,
  "task_run_id": "task-run-710",
  "fork_stack": [
    {"fork_instance_id": "fork-411", "fork_node_id": "split", "merge_node_id": "combined", "branch_index": 1}
  ],
  "next_check_at": "2026-11-20T20:00:05Z",
  "lease_owner": null,
  "lease_until": null,
  "created_at": "2026-11-20T20:00:00Z",
  "updated_at": "2026-11-20T20:00:01Z"
}

visit_seq увеличивается при новом входе в узел на цикле или после перехода согласно внутреннему правилу; важна уникальность пары point_id + visit_seq + attempt для идемпотентного обращения к Task. Внешняя машина хранит и использует именно DB-поля; JSON выше — API/диагностическое представление.

9.2. Состояния точки

Состояние Значение Может планироваться диспетчером?
READY Есть доступная вершина и данные; переход ещё не обработан Да
CLAIMED Временная DB-аренда worker для атомарного шага Нет для других worker
WAITING_TASK Существует поставленная в очередь/выполняемая Task VALERIA Только проверка статуса по времени/событию
WAITING_MERGE Результат ветви прибыл и сохранён у барьера Нет
FORKED Исходная точка поглощена Fork после создания N дочерних Нет, терминальное для точки
CONSUMED Точка поглощена Merge или достигла end Нет, терминальное для точки
FAILED Ошибка узла/перехода Нет
CANCELLED Остановлена из-за отмены Run Нет

Рабочая аренда CLAIMED лучше хранится как status=READY плюс lease-поля, но может представляться отдельным UI-состоянием для мониторинга. В любом случае после истечения lease при сбое worker точка повторно доступна на безопасной, идемпотентной операции.

9.3. Состояния всего Pipeline Run

CREATED → RUNNING → одно из SUCCEEDED, FAILED, CANCELLED.

Дополнительное переходное состояние CANCEL_REQUESTED рекомендуется. CREATED становится RUNNING после фиксации стартовой точки. SUCCEEDED означает, что все законные конечные пути завершены, активных/ожидающих точек и открытых Fork нет, итоговый выход зафиксирован. FAILED означает фатальную ошибку хотя бы одного обязательного шага по выбранной политике fail_fast. CANCELLED означает завершённую отмену.

У Run нет одного глобального node_id, он определяется множеством точек. Счётчики active_points, waiting_tasks, waiting_merges, completed_tasks — производные агрегаты, а не источник истины.

9.4. Пример переходов

Run RUNNING
  Point 10: READY@Transform
    └─ execute transform, commit
  Point 10: READY@Fork
    └─ create fork_instance F1 + Point 11/12/13, mark Point10 FORKED
  Point 11: READY@TaskA -> WAITING_TASK(job 501)
  Point 12: READY@TaskB -> WAITING_TASK(job 502)
  Point 13: READY@TaskC -> WAITING_TASK(job 503)

  job 502 completed -> Point12 WAITING_MERGE(F1, branch 1)
  job 503 completed -> Point13 WAITING_MERGE(F1, branch 2)
  job 501 completed -> Point11 WAITING_MERGE(F1, branch 0)

  F1 all arrived -> Point14 READY@next_after_Merge, Points11/12/13 CONSUMED
  Point14 ... -> end -> CONSUMED
Run SUCCEEDED

Ни один вызов ожидания не должен удерживать поток HTTP-запроса или слот OpenCode. HTTP запускает Run, а дальнейшее выполнение происходит в фоновом внутреннем цикле диспетчера приложения, который является обычной частью процесса VALERIA. После рестарта он восстанавливается из БД; отдельный «внешний агент-запускатель» не нужен.

9.5. Аренда и выбор очередной точки

Диспетчер периодически выбирает READY и WAITING_TASK с наступившим next_check_at; сначала выполняет атомарный claim точек по уникальному token и lease_until, затем отдельную короткую операцию. Нельзя держать DB transaction открытой, пока исполняется LLM-задание или сетевой запрос. После завершения локального шага данные, новый node/status и событие фиксируются одной транзакцией. Важна конечная справедливость между пайплайнами и пользователями: длинный цикл из Transform не должен монополизировать поток обработки.

В SQLite применяются WAL, busy_timeout, короткие транзакции и атомарный UPDATE ... WHERE lease_until < now RETURNING ... или эквивалент CAS. SELECT FOR UPDATE SKIP LOCKED не поддерживается SQLite и не используется как обязательная технология. Размер batch и число scheduler-worker настраиваются.

9.6. Две разные формы асинхронности

  • Диспетчер VFlow: быстро и локально выполняет оператор или регистрирует ожидание; может обслуживать тысячи ожидающих точек, не занимая тысячи потоков.
  • Общая очередь VALERIA: независимо ограничивает число одновременно выполняемых OpenCode-сессий по существующим лимитам. Несколько Task из Fork могут оказаться в очереди и запускаться по FIFO в зависимости от доступных слотов. Fork не гарантирует физически одновременного выполнения всех N агентов.

10. Восстановление после сбоя, повторные запросы и идемпотентность

10.1. Ключевые гарантии

Систему следует строить по принципу at-least-once processing + idempotent state transitions, а не обещать «ровно один вызов внешней системы» без подтверждения её идемпотентности. Для логических переходов внутри SQLite достигается effectively-once через транзакции, уникальные ключи и CAS. Для побочных эффектов внешних Task строгое exactly-once может быть недостижимо, особенно если агент выполнил действие, но подтверждение было утеряно.

10.2. Повторный запуск по HTTP

POST /api/pipelines/{id}/runs обязан поддерживать Idempotency-Key в рамках пользователя. Повтор с тем же ключом и тождественным телом запроса возвращает тот же run_id; тот же ключ с другим телом возвращает 409 IDEMPOTENCY_CONFLICT. Ключ хранится вместе с хешем нормализованного запроса и идентификатором опубликованной версии.

10.3. Повторный вход worker в Task

До постановки задачи создаётся durable intent/ключ. Если ответ из очереди на постановку неизвестен, VFlow сначала ищет задачу по ключу/метке и не делает новый POST, пока не станет известно, что предыдущий не был принят. Это согласовано с текущей моделью VALERIA, где повторная выдача задачи после неопределённого сетевого результата не должна удваивать работу.

Возможные варианты атомарности:

  1. Общая SQLite-транзакция: создать запись таски + записать task_run_id и состояние точки атомарно (при наличии прямого внутреннего метода очереди).
  2. Transactional outbox: записать в БД VFlow команду enqueue_task и точку; отдельный отправитель доставляет команду по стабильному идемпотентному ключу; ответ связывается с точкой; незавершённые команды восстанавливаются.

Нельзя оставлять простой сценарий «HTTP POST задачи → crash → повторно POST» без идемпотентного ключа и сверки.

10.4. Повторный Fork

Уникальный (run_id, parent_point_id, visit_seq, fork_node_id) в таблице fork_instances предотвращает дублирование fork-instance. Создание N потомков и поглощение родителя — одна транзакция; при повторном claim система видит существующий instance и не создаёт вторую группу.

10.5. Повторный Merge

Уникальный (fork_instance_id, branch_index) запрещает двойное прибытие одной ветки. Только операция CAS OPEN -> MERGED, выполняемая в одной транзакции с созданием продолжающей точки, может выпустить результат. При двух параллельных обработчиках завершения разных веток лишь один совершит выпуск.

10.6. Recovery pass

После старта приложения:

  1. Загрузить все незавершённые Run.
  2. Сбросить только просроченные leases; активные не трогать.
  3. Проверить все WAITING_TASK, у которых наступило время опроса; восстановить связь с текущими VALERIA Task Run по сохранённому ID/idempotency marker.
  4. Проверить все открытые Fork и Merge, у которых все arrivals уже сохранены, но выпуск ещё не произведён; добить CAS-сверку.
  5. Восстановить outbox-сообщения и расписание ретраев.
  6. Пересчитать агрегаты Run, проверить аномалии (например RUNNING без живых точек) и зафиксировать диагностическое событие.
  7. Продолжить обычную обработку; не запускать снова уже принятые в VALERIA задачи.

10.7. Отмена

CANCEL_REQUESTED блокирует создание новых Task Run. Для текущих Task Run запрашивается отмена через доступный Gateway; если фактическая отмена внешней системы недоступна, фиксируется cancellation_pending и/или detached_external_task в админ-аудите. Все ожидающие/готовые точки переводятся в CANCELLED, дальнейшие arrivals не дают создать новый downstream Task. Отмена должна быть повторяемой, идемпотентной и авторизованной. При известном подтверждённом состоянии Run становится CANCELLED; нельзя ложно утверждать, что реальные внешние side effects отменены, если это не подтверждено.

10.8. Ошибка одной ветки и fail-fast

В v1 применяется fail_fast по умолчанию: когда обязательный Task/Transform/If/другой оператор завершился с неизлечимой ошибкой, весь Pipeline Run переходит к FAILED; оставшиеся ветки не продолжают переходы и новые Task не запускаются. Уже выполняющиеся внешние Task могут требовать отдельного запроса на отмену. Merge не выдаёт «успешный» выход на частичном наборе. Будущая поддержка «ошибка как данные» возможна только как явно спроектированное расширение языка, не скрытое изменение поведения Merge.

10.9. Временные сбои опроса Task

Транспортная ошибка проверки Task Run не является подтверждённой ошибкой самой задачи. Периодический опрос с backoff и jitter продолжает проверку до восстановления связи, явной отмены или исчерпания отдельно настроенного инфраструктурного лимита. Технический WAITING_TASK не блокирует другие точки. Максимальная задержка опроса может согласовываться с принятым в существующей VALERIA backoff, но callback/status event должен будить точку быстрее при возможности.

11.3. Влияние параллельности на workspace

Несколько дочерних Task одной ветки Fork могут работать в одном и том же workspace пользователя. По умолчанию можно оставить поведение существующей очереди и workspace, но редактор должен показывать предупреждение при параллельных задачах с возможными side effects. Рекомендуемые последующие политики: shared_readonly, exclusive_workspace, isolated_worktree, isolated_copy. Это не замена контейнерной песочницы.

12. Хранение в SQLite

12.1. Принцип хранения

Граф обязательно хранится в БД и версионируется. Канонический источник истины — graph_ir_json в pipeline_versions; можно дополнительно строить представления/индексы для поиска по узлам, но они не должны расходиться с каноническим IR. Позиции UI и выбранные настройки включаются в IR/метаданные версии. Исходный текст vflow_source сохраняется рядом для удобства, но исполнение производится по проверенному IR, а не по пользовательскому исходнику в момент Run.

Активные точки, fork-instance, arrivals и связи с Task Run — отдельные долговечные записи. Нельзя хранить всё runtime-состояние только одним mutable JSON в строке Run: это усложнит атомарные Fork/Merge, восстановление и параллельные изменения разных точек.

12.4. Жизненный цикл данных

  • Публикуемые версии хранятся долго, минимум пока на них ссылаются Run.
  • История запусков хранится по заданной политике retention, без удаления записей, на которые опираются активные точки.
  • Архивация пайплайна не уничтожает историю.
  • Удаление промежуточных JSON и событий производится отдельным retention job только после завершения Run и с учётом требований аудита.
  • Административный экспорт для диагностики должен редактировать/маскировать секреты, персональные данные и внутренние промпты.

13.3. Короткий цикл обработки точки — псевдокод

async def scheduler_tick():
    candidates = await repository.claim_due_points(limit=WORK_BATCH_SIZE)
    for point in candidates:
        await process_claimed_point(point)

async def process_claimed_point(point):
    run = await repository.get_run(point.run_id)
    if run.status in {"CANCEL_REQUESTED", "CANCELLED", "FAILED"}:
        await repository.mark_cancelled_or_consumed(point)
        return

    plan = await repository.load_immutable_plan(run.pipeline_version_id)
    node = plan.node(point.node_id)
    handler = registry.get(node.type, node.type_version)

    # Никаких прямых произвольных SQL/изменений состояния со стороны handler.
    action = await handler.plan(point=point, node=node, runtime=restricted_runtime_context())
    await repository.apply_action_atomically(point, action)

plan должен быть чистым/безопасным для операторов без side effects. Для узла Task side effect «постановка задачи» оформляется через action/outbox и не исполняется произвольно в handler.plan. Иначе crash между enqueue и коммитом состояния может дублировать работу.

Движок переводит точку в нужное состояние по результату handler, но только после проверки идемпотентности, бюджета переходов, допустимости портов и валидности выходного JSON.

13.4. Атомарные действия Runtime

Handler возвращает одно из типизированных действий, а центральный Runtime сохраняет их последствия:

Action Что делает Runtime
Advance(port, output_json) Передвигает ту же точку по указанному ребру, сохраняет JSON и событие
EnqueueTask(task_request) Фиксирует команду enqueue с ключом и переводит точку в WAITING_TASK
Suspend(kind, wake_condition) Сохраняет ожидание без занятых worker
SpawnFork(n, join_node_id, input_json) В одной транзакции создаёт fork-instance и N точек, поглощает родителя
ArriveMerge(fork_instance_id, branch_index, data_json) Сохраняет arrival; возможно выпускает одну продолжающую точку
Finish(output_json) Поглощает точку на терминале, проверяет завершение Run
Fail(error_code, safe_message, internal_context) Фиксирует ошибку и запускает политику fail-fast

SpawnFork и ArriveMerge — привилегированные действия, проверяемые структурой графа. Обработчик не может просто «сделать UPDATE points SET ...» вне Repository; это минимизирует ошибки будущих расширений.

13.5. Модель ожидания

  • Task ожидается по persisted task_run_id и wake event/next_check_at.
  • Merge ожидается по persisted arrivals; после последней arrival возобновление выполняется транзакцией, не busy-loop.
  • Новые типы Delay/WaitForEvent в будущем используют то же Suspend и долговечное состояние, не создавая вечные фоновые Python-корутины на каждый Run.
  • Состояние Run восстанавливается после рестарта из БД; никакая критическая информация не может существовать только в памяти процесса.

13.6. Справедливость и изоляция между запусками

При многочисленных READY-точках scheduler должен применять ограничение batch per run и при необходимости per user, чтобы один многоразветвлённый граф не вытеснил остальные. Общая очередь задач VALERIA продолжает управлять реальным лимитом OpenCode. Контекст пользователя и workspace всегда устанавливается сервером из Run, а не берётся из произвольного data_json.

14. Расширение языка: разработчик добавляет новые типы блоков

14.1. Обязательное требование

В будущем именно автор/разработчик VALERIA должен иметь возможность реализовать новые системные блоки. Никакой конечный пользователь, редактор пайплайнов или обычный администратор не может загрузить код такого блока, вставить Python/JS в интерфейс и тем самым расширить серверный язык.

Расширяемость должна быть архитектурной и code-first: разработчик добавляет Python-модуль с Node Handler, описывает контракт блока в Registry, тестирует, выпускает релиз и деплоит обновлённую VALERIA. После обновления блок появляется в палитре редактора и становится доступен для новых версий пайплайнов. Новые редакторы отдельных блоков не должны требовать изменения общего UI-кода, если стандартная форма по JSON Schema достаточна.

14.2. Контракт регистрации типа блока

Новая запись Registry обязана содержать:

Поле Назначение
type_id Стабильное namespace-имя (core.if, core.transform, custom.delay)
version Семантическая версия контракта блока (1.0)
display_name, description, icon, category Палитра администратора
config_schema JSON Schema настроек, валидируемая на сервере
input_schema, output_schema Описание допустимых данных / формат для подсказок
ports Список входов/выходов, динамическое правило портов при необходимости
handler_factory Фабрика обработчика выполнения
validator Дополнительная compile-time проверка параметров/связей
execution_kind synchronous, async_wait, fork, barrier и т. п.
capabilities Разрешённые внутренние возможности, минимально необходимые handler
idempotency_contract Гарантии повторного вызова и реконструкции состояния
migration_policy Какие старые версии конфигураций поддерживаются

Важно: Task — отдельный встроенный адаптер valeria.task, а не возможность админа загрузить новый Python-обработчик произвольной таски.

14.3. Пример Python API (предлагаемый, не существующий)

from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class NodeSpec:
    type_id: str
    version: str
    display_name: str
    category: str
    config_schema: dict
    ports: dict
    execution_kind: str

class NodeHandler(Protocol):
    spec: NodeSpec

    def validate(self, config: dict, graph_context: object) -> list[object]: ...

    async def plan(self, point: object, config: dict, runtime: object) -> object: ...

# Разработчик создал новый системный блок в исходниках VALERIA:
class DelayHandler:
    spec = NodeSpec(
        type_id="custom.delay",
        version="1.0",
        display_name="Delay",
        category="Control",
        config_schema={
            "type": "object",
            "properties": {"seconds": {"type": "integer", "minimum": 1, "maximum": 86400}},
            "required": ["seconds"],
            "additionalProperties": False,
        },
        ports={"inputs": ["in"], "outputs": ["out"]},
        execution_kind="async_wait",
    )

    def validate(self, config, graph_context):
        return []

    async def plan(self, point, config, runtime):
        return runtime.suspend_for(seconds=config["seconds"],
                                   resume_port="out", output=point.data)

registry.register(DelayHandler)

Это иллюстрация будущего нового типа, не часть обязательных стартовых четырёх операторов и не обещание реально существующей функции runtime.suspend_for. При реализации нужно обеспечить воспроизводимое вычисление дедлайна: повторный вызов после crash должен читать ранее сохранённый deadline, а не каждый раз откладывать время заново.

14.4. Почему контракт plan -> Action, а не прямое изменение БД

Обработчик не должен напрямую удалять/создавать точки, обходить authorization или запускать Task без idempotency. Он возвращает допустимое действие; общий Runtime проверяет переходы, сериализацию, права и лимиты, а затем транзакционно применяет действие. Отдельные расширения, которым необходим доступ к сети или filesystem, должны получить явные capabilities и проходить отдельный аудит безопасности. Базовые Transform/If должны оставаться чистыми.

14.5. Версионирование и совместимость блоков

  • Все опубликованные Pipeline Version хранят type_id и точную поддерживаемую версию handler, использованную при компиляции.
  • Новая реализация блока с меняющейся семантикой должна иметь новую версию (core.transform@2.0), а не тихо менять @1.0.
  • На сервере должны оставаться старые обработчики, пока существуют активные Run/публикации, использующие их, либо должна существовать явная, проверенная миграция.
  • Обновлённый UI получает Registry-манифест от API, не основываясь на захардкоженном списке для всех будущих блоков.
  • Удаление/отключение типа с активными зависимостями блокируется или требует миграционной процедуры; неизвестный тип не заменяется «пустым узлом».
  • Администратор видит предупреждение «обновление блока доступно» и может создать новую версию пайплайна с миграцией конфигурации; старый активный Run при этом продолжает на прежнем обработчике.

14.6. UI расширений

Для стандартных блоков интерфейс строит форму по JSON Schema: строка, number, boolean, enum, массив, object, подсказки, валидация. Для сложных новых типов разработчик может включить доверенный frontend-компонент в поставку VALERIA и зарегистрировать его вместе с типом, но нельзя позволять администратору загружать сторонний JavaScript через веб-форму. В палитре четко различаются «Системные операторы» и «Задачи VALERIA».

14.7. Как добавляется будущий блок — процедура разработчика

  1. Придумать type_id и версию без конфликта существующих имён.
  2. Описать JSON-контракт входа/выхода, порты и config_schema.
  3. Реализовать validate и plan, возвращающие типизированные Runtime Actions.
  4. Зарегистрировать обработчик в Python Registry.
  5. Поддержать DSL-вызов через таблицу имён (delay(...) → custom.delay), без изменения общей грамматики аргументов и рёбер.
  6. Добавить/зарегистрировать отображение в палитре и инспекторе.
  7. Написать тесты корректной работы, ошибок, идемпотентного повтора, рестарта и ограничений доступа.
  8. Выпустить версию приложения и миграцию при необходимости.
  9. Только после деплоя новый блок доступен администратору для новых схем.

Таким образом расширение языка не требует пересматривать базовую модель точек, графа или сохранения состояния.

14.8. Эволюция синтаксиса

DSL-компилятор регистрирует имя функции блока (if, transform, fork, merge, task.run, delay, ...) в таблице допустимых call forms. Общий синтаксис step id = block_name(args) остаётся прежним. Новые конструктивные формы, которым нужны дополнительные рёбра/порты, объявляются метаданными блока, а не правкой парсера для каждого нового типа. Только действительно новые синтаксические конструкции языка требуют повышения версии DSL.

16. Безопасность

16.1. Разделение областей доверия

  1. User input JSON — недоверенные данные.
  2. VFlow DSL / IR — редактируется только администратором, но всё равно проходит строгую проверку и не исполняется как Python/JS.
  3. Task definitions/prompts — внутренние данные VALERIA; не выдаются ordinary users.
  4. Node Handlers — доверенный код, поставляемый только разработчиком, версионированный и тестируемый.
  5. OpenCode/MCP/workspace — внешняя среда исполнения со своими правами и рисками.

16.2. Права

Сервер повторно проверяет публикацию, аудиторию, право на Run, право отмены, принадлежность workspace, разрешение на Task в данной версии и лимиты. Отредактировать HTTP-request вручную не должно позволить запустить скрытый/чужой Pipeline или произвольную Task ID. Возможность просмотра административного графа требует отдельного admin-check на API, не просто скрытия вкладки.

16.3. Безопасный DSL

  • Запрещены eval, exec, import, произвольный shell, SQL и возможность обращения к internals Python/JS.
  • JSONPath — ограниченный subset, строго интерпретируемый над JSON.
  • Transform работает только с данными; HTTP/файлы — задачи VALERIA или будущие доверенные code-first блоки.
  • JSON-строки сериализуются и экранируются; UI использует safe text rendering, а не innerHTML для недоверенного JSON.
  • Размеры и глубина JSON ограничены; глубину тоже следует лимитировать (рекомендация 64).

16.4. Секреты и вывод

Любое значение из task output может содержать секреты/персональные данные. Администратор имеет полномочия диагностики, но даже админ-UI должен избегать случайного вывода секретов в browser logs и экспортах. Публичный результат требует отдельной public_result_schema, явного выбора разрешённых полей или проверенного sanitizer; статус по умолчанию безопасен. Ошибки пользователю — нейтральные; внутренний traceback только администратору, с фильтрацией секретов.

16.5. Ограниченность изоляции workspace

Текущая VALERIA отдельно отмечает, что назначение cwd и policy OpenCode не являются полноценной песочницей. Модуль VFlow не должен обещать обратное. Fork с несколькими AI Task увеличивает число параллельных агентов и потенциально коллизии файлов; не требуется вручную выдавать новые filesystem-права и нельзя обходить существующие workspace-root ограничения.

16.6. CSRF, IDOR, concurrency, DoS

Существующая сессионная авторизация должна сопровождаться применяемой в VALERIA CSRF-защитой на mutation routes; каждый Run запрашивается только владельцем/администратором; user-supplied ID не используется без проверки; scheduler имеет лимиты на количество точек и переходов; SQL — параметризованный; записи схем графа ограничены по размеру; все внешние callback ID валидируются. Нельзя передавать workspace_id из пользовательского JSON напрямую на исполнение без проверки.

17. Наблюдаемость и диагностика

17.1. Журнал событий

Каждый существенный переход фиксируется отдельным событием с UTC-временем, run_id, point_id, node_id, event_type, request_id/correlation_id, безопасной диагностикой. События позволяют восстановить хронологию, не переписывая состояние. При переполнении интерфейс подгружает последние записи с пагинацией; сам runtime опирается на таблицы точек/форков/тасок, а не воспроизводит состояние целиком из журнала в MVP.

17.2. Метрики

Метрики для администратора/оператора:

  • количество определений, опубликованных версий и Run по статусам;
  • время Run от принятия до завершения, отдельно queue wait и actual Task execution;
  • число активных точек, WAITING_TASK, WAITING_MERGE, Task Run по одному Pipeline Run;
  • распределение времени ожидания Task и Merge;
  • количество развилок и ширина Fork;
  • число ошибок по типам блоков и кодам;
  • количество retry, expired lease и recovery reconciliation;
  • нагрузка на общую очередь VALERIA, вызванная пайплайнами;
  • число остановленных лимитом циклов и JSON-size violations.

Для пользователя публикуются только агрегированные разрешённые показатели, не внутренний граф. Необходимы ключи корреляции pipeline_run_id, pipeline_point_id, origin_pipeline_node_id у дочерних VALERIA Task Run в админ-диагностике. При этом существующая статистика задач VALERIA может продолжать учитывать каждый дочерний Task отдельно; статистика VFlow должна быть отдельной и не путать число пайплайнов с числом задач.

17.3. Отладочный режим администратора

Администратор выбирает Pipeline Run и видит снимок точек на сохранённой версии графа: на каждом узле badges со счётчиками (2 running, 1 waiting), по клику — point ID, branch index, parent, task run status, время и безопасный предпросмотр JSON. Скрытые промпты можно смотреть только через разрешённый админ-раздел VALERIA; VFlow не обязан их дублировать. Журнал должен отличать «оператор выполнен» от «задача лишь поставлена в очередь».

18. Подробные сценарии исполнения

18.1. Последовательный пайплайн Task → Transform → If

Начало: Пользователь выбирает опубликованный пайплайн и отправляет { "ticket_id": 24 }.

  1. API проверяет пользователя, аудиторию, JSON Schema и идемпотентность запроса.
  2. Создаёт Run версии V5 и Point P1 на первой Task, статус READY.
  3. Scheduler берёт P1, пишет задачу T1 в существующую очередь и переводит P1 в WAITING_TASK.
  4. Внешняя очередь VALERIA запускает T1, когда доступен слот OpenCode.
  5. VFlow не держит занятым свой worker; другие точки/Run продолжаются.
  6. T1 завершается, Gateway отдаёт финальный текст. VFlow строго/мягко парсит JSON по настройке узла и конструирует конверт {"input":...,"task":...}.
  7. P1 продвигается на Transform, где из $.task.output.json.score формируется нужная структура.
  8. P1 на If читает конкретное поле входа, вычисляет условие и идёт по одной из двух дуг без изменения JSON.
  9. P1 достигает end, его состояние CONSUMED; Run при отсутствии прочих активных точек завершается SUCCEEDED.
  10. UI показывает завершение, по политике — только статус или разрешённый публичный результат.

18.2. Параллельная проверка из трёх Task

Start -> Prepare -> Fork(3) --branch[0]--> Task Review --\
                            --branch[1]--> Task Tests  ---+--> Merge -> If -> End
                            --branch[2]--> Task Security-/

В момент Fork внутри одной DB-транзакции создаются P2, P3, P4. Их начальные data равны по JSON-значению, а branch_index — 0, 1, 2. P2/P3/P4 независимо ставят три реальные Task VALERIA в очередь. Task могут исполняться по-разному быстро (и не обязательно одновременно). Результат Task Tests приходит первым — создаётся arrival индекса 1 и P3 ждёт Merge. Security — второй; Review — последний. Только после arrival индекса 0 Merge создаёт одну P5 с branches в порядке 0,1,2. Если один Task упал, общий Run получает FAILED и Merge не выдаёт downstream output.

18.3. If внутри Fork

Fork(2) --branch[0]--> If ---> Task A --\
                       | false -> Task B --+-> Merge
         --branch[1]--> Task C ------------/

Правило: If не удаляет ветку и не создаёт новую. Для branch[0] реально выполняется один путь A или B, после чего та же ветка с index 0 попадает в Merge. branch[1] независимо достигает Merge с index 1. Merge ждёт две уникальные ветки, а не три возможных маршрута. Если одна дуга If ведёт в End вместо Merge, публикация отклоняется.

18.4. Два одновременных запуска одного графа

Run R1 и R2 используют одну Pipeline Version, но имеют разные input, точки, Fork Instances и Task Run. Даже если оба одновременно находятся в узле combined и у каждого N=3, их arrivals не могут смешаться. Ключ синхронизации включает run_id через собственный fork_instance_id.

18.5. Повторный вход в Fork после цикла

Если граф позволяет после закрытого Merge пройти через If и снова достичь того же Fork, создаётся новый fork_instance_id с новым parent_visit_seq, даже внутри того же Run. Старые arrivals остаются историей и не считаются прибытием к новому Merge. Это обязательное свойство state-machine, а не обычной единожды вычисляемой DAG.

18.6. Падение сервера после постановки Task

Уже принят Task VALERIA, но HTTP/worker упал перед сохранением task_run_id. После рестарта VFlow видит durable intent, восстанавливает задачу по idempotency marker/ключу в общей очереди, привязывает первоначальную Task Run и продолжает ожидание. Вторая Task не создаётся. Если нет подтверждённого знания о принятии, система продолжает сверку вместо немедленного повторного создания.

18.7. Две последние ветки пришли одновременно

Worker A пишет arrival ветки 1; worker B одновременно — arrival ветки 2. DB уникальные ограничения и атомарный OPEN -> MERGED гарантируют, что у Fork появится одна продолжающая точка. Даже при повторном wake callback она не удвоится. Разработка должна иметь автоматический тест этой гонки.

18.8. Администратор публикует новую версию во время Run

R1 использует V5, администратор публикует V6. Новый R2 использует V6, R1 продолжает строго по IR V5. Изменение task_id, количества веток или выражений If в V6 не изменяет R1. Публикация V6 не должна сбрасывать fork_stack и waits R1.

18.9. Удалённый или отключённый тип блока

Если граф содержит тип custom.delay@1.0, а деплой более не содержит такой обработчик, публикация/новый запуск такой версии запрещаются с внятной админ-диагностикой. Активные Run требуют прежнего совместимого handler; если его действительно нет, их нельзя тихо продолжать через заглушку. Деплой должен проверять наличие обработчиков для активных версий на этапе запуска/healthcheck. Удаление handler до завершения зависимых Run — ошибка процедуры обновления.

19.4. Нагрузочные испытания

Проверить не только «граф красиво рисуется», но и реальное поведение state machine:

  • 100 одновременных Run с Fork(3), без превышения общих лимитов OpenCode;
  • массовые WAITING_TASK без пропорционального числа asyncio task/threads, спящих часами;
  • параллельные arrivals Merge с random задержкой и искусственными crash;
  • SQLite busy_timeout и конкуренция транзакций (ожидаемые короткие lock waits);
  • сохранение/восстановление Run с сотнями событий и сменой версии;
  • остановка и рестарт приложения на каждой критической границе: до/после enqueue, после Fork, перед/после release Merge;
  • отсутствие очередного запуска Task после повторного delivery webhook/status-event;
  • корректный backpressure на очереди с ограниченным числом OpenCode-сессий.

19.5. Минимальное определение готовности (Definition of Done)

  1. Оба раздела меню доступны нужным ролям, серверные авторизации проверены.
  2. Админ создаёт и публикует workflow через UI; граф хранится в БД.
  3. Тот же workflow представим в поддерживаемом VFlow DSL с компиляцией в один IR.
  4. В палитре ровно 4 стартовых системных оператора и живой каталог существующих Task VALERIA.
  5. Task ставится через исходную очередь, сохраняет task_run_id, ожидается без блокировки других точек и Run.
  6. Fork создаёт N дочерних точек последовательно и атомарно.
  7. Merge ждёт все N веток конкретной активации, не выпускает частичные результаты и выдаёт одну точку.
  8. If проверяет поле входного JSON, не меняя этот JSON.
  9. Transform меняет JSON предсказуемым, безопасным способом.
  10. Рестарт в любой критической точке не дублирует логические Fork/Merge и не создаёт повторную внешнюю Task без гарантии уникальности.
  11. Пользователь может только запускать опубликованные доступные пайплайны и смотреть разрешённые статусы своих Run, без права редактировать/видеть исходный граф.
  12. Добавление нового типа блока автором через Registry и деплой не требует переписывания исполнения точек и автоматически отражается в UI.
  13. Все тесты разделов 19.1–19.3 проходят; документация API, БД и миграций обновлена.

Появляются ли новые блоки в UI автоматически? Да, из доверенного серверного Registry после деплоя.
Можно ли обновлять активный граф на месте? Нет, Run закреплён за immutable Pipeline Version.
Может ли граф иметь циклы? Да, при структурно корректных Fork/Merge и runtime лимитах.

21.1. Что является архитектурным предложением, а не сообщённым ранее требованием

В документе дополнительно предложены: имена REST API и таблиц; хранение графа как Graph IR JSON в версии; снимок Task-конфигураций на старте Run; дефолтная форма JSON-convert для Task/Merge; exact-формы DSL; fail-fast по умолчанию; ограниченный JSONPath; numeric limits; правила structured Fork/Merge; политика публичной выдачи результатов; механизм делегирования права на внутренние Task; lease/outbox/recovery и schema-driven UI. Эти решения выбраны для полноты реализуемой спецификации и не должны интерпретироваться как существующий функционал репозитория.

21.2. Критические проектные проверки перед кодированием

  1. Есть ли у текущего диспетчера VALERIA внутренний API для получения финального ответа Task Run без раскрытия пользователю? Если нет — добавить.
  2. Можно ли атомарно создать существующий Task Run и связать его с точкой VFlow в одной БД? Если нет — использовать outbox и идемпотентную сверку.
  3. Как именно текущая система сохраняет task definition snapshot? При необходимости расширить внутреннюю модель, чтобы уже запущенный пайплайн использовал консистентные Task-настройки.
  4. Как реализованы аудитории задач, tasks_only, CSRF и workspace права в актуальном коде? Использовать действующие проверки, не создавать параллельную «слабую» модель.
  5. Как текущая установка выполняет миграции SQLite? Новые таблицы должны добавляться в общем механизме без потери существующих данных.
  6. Как эффективно извлекать результат Task в формате JSON при LLM-ответе с markdown? Для strict_json запретить неявное извлечение из произвольного блока кода; парсить полный ответ либо явно настроенный формализованный envelope.
  7. Чем ограничить внешние side effects при многопоточном Fork в одном workspace? Минимум — предупреждение, далее — locking/isolated worktrees по необходимости.

22. Итоговое архитектурное определение

VFlow — встроенный модуль VALERIA, реализующий сохраняемую в SQLite графовую машину состояний. Администратор создаёт и публикует граф через визуальный редактор в стиле n8n либо через декларативный DSL. Обычные пользователи имеют отдельную вкладку только для запуска опубликованных пайплайнов и просмотра разрешённого статуса своих запусков. Каждый Pipeline Run закреплён за неизменяемой версией графа и может иметь одновременно несколько независимых точек выполнения. Task ставит существующую задачу VALERIA в общую очередь и ждёт завершения; Transform изменяет JSON; If выбирает путь по полю JSON, не изменяя данные; Fork N последовательно и атомарно создаёт N дочерних точек; Merge ждёт достижения барьера всеми N ветками конкретного Fork Instance, формирует упорядоченный JSON и продолжает исполнение одной точкой. Runtime обеспечивает восстановление после сбоев, транзакционную идемпотентность, ограничение ресурсов, контроль доступа и версионирование схем.
