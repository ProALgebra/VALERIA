**Статус:** рабочий план, не описание уже реализованного функционала
**Дата:** 20 ноября 2026 г.
**Основание:**
- `docs/VALERIA_VFlow_Technical_Specification_RU.md` — требования, модель данных, DSL, runtime, API и критерии приёмки;

## 1. Главные выводы перед началом

### 1.1. Что уже есть в репозитории и что придётся переиспользовать

| Область | Фактическое состояние | Как использовать в VFlow |
|---|---|---|
| Веб-приложение | Один FastAPI-приложение в `src/opencode_web/app.py`, фабрика `create_app()`, маршруты объявлены внутри неё | Добавить `vflow`-роутеры и зависимости в тот же `create_app`, не поднимать отдельный сервис |
| Интерфейс | SPA: `static/index.html` + `static/app.js` + `static/styles.css`, hash-маршруты, без Jinja-шаблонов | Встроить новые экраны как модули SPA; макет v2 перенести в отдельный CSS/JS-модуль |
| Аутентификация | Cookie-сессия, `current_principal`, `csrf_principal`, `admin_principal` | Переиспользовать; для mutation-маршрутов обязателен `X-CSRF-Token` |
| Роли | `users.role` (`user`/`admin`), `users.tasks_only` | Добавить проверки VFlow; `tasks_only` должен получить доступ к пользовательской вкладке «Пайплайны» |
| SQLite | Единая схема `SCHEMA` в `database.py`, миграции через `initialize()` и `ALTER TABLE`, одно соединение с `RLock`, `transaction()` использует `BEGIN IMMEDIATE` | Новые таблицы добавлять в общий механизм; runtime-транзакции выполнять через `Database.transaction()` |
| Очередь задач | `queue_jobs` — общая FIFO-очередь; `create_task_job`, `claim_next_job`, `complete_task_run`; статусы `queued`/`running`/`completed`/`failed`/`cancelled` | VFlow не запускает OpenCode напрямую: только создаёт обычный `queue_jobs`, ждёт терминального статуса |
| Результат задачи | `task_run_results` + `complete_task_run` + `task_final_answer()` | Через внутренний gateway читать только финальный текст; JSON-парсинг выполнять по `result_mode` |
| Старая «pipeline»-механика | `tasks.task_successors`, `queue_jobs.pipeline_json`, `_enqueue_pipeline_children()` автоматически создают дочерние задачи после `completed` | **Не путать с VFlow.** Для VFlow-задач отключить авто-порождение детей, иначе один узел создаст лишние Task Run |
| Идемпотентность HTTP | `submissions` (`actor_id`, `request_key`, fingerprint, response) | Переиспользовать идею для `POST /runs`; дополнительно хранить `pipeline_run_id` и версию |
| События | `EventBroker` — in-memory SSE, события `job.updated` | Использовать для быстрого пробуждения UI/runtime, но источник истины — БД; polling обязателен |
| Тесты | `pytest`, API-тесты, Playwright browser-тесты | Добавить unit/API/DB/Playwright-тесты по матрице §19 спецификации |

### 1.2. Расхождения между макетом и нормативной спецификацией

Макет — концепт, а не контракт. Перед реализацией нужно принять решения:

1. **DSL.** В макете показан `task context = valeria.task(...)`, `transform payload = map(...)`, `fork copies = duplicate(...)`, `parallel { ... }`, `merge results = join(...)`, `if (...) { ... }`. Нормативный язык — §8: `step id = task.run(...)`, `step split = fork(count: N, join: ...)`, `step combined = merge()`, `step decision = if(path: ..., operator: ..., value: ...)`, связи `a -> b`, порты `if.true`, `fork[0]`. **Реализуем §8, а code-view макета приводим к каноническому виду.**
2. **Merge.** В макете есть режим `First success`. Спецификация v1 требует только строгий `wait_all`; first-success запрещён. Убрать из формы или пометить как недоступное будущее расширение.
3. **Transform/If.** В макете — произвольные JS-подобные выражения (`input.every(item => item.ok === true)`). Спецификация требует декларативные операции Transform и `path/operator/value/missing` для If, без eval/exec. Заменить инспекторы на безопасные формы.
4. **Fork.** В макете N ограничено 2–5 для демонстрации; в спецификации `2 ≤ N ≤ max_fork_n` (рекомендуемый старт 32). Сделать N конфигурируемым, демо-диапазон оставить только как UX-подсказку.
5. **Верхняя панель.** В макете только «Сохранить» и «Запустить»; по §5.3 нужны версия, draft/published, undo/redo, «Проверить», «Опубликовать», «Запустить».
6. **История.** В макете — демо-список; по §5.2/§15 нужны собственные Run пользователя, фильтры, пагинация, безопасные статусы и отмена по политике.
7. **Настройки публикации.** В макете нет input schema, public result schema, аудитории, лимитов; по §5.3/§5.5 это часть административного редактора.
8. **Отображение Run.** Нельзя рисовать одну «бегущую стрелку»: на одном узле может быть 0, 1 или несколько execution points. Нужны badges/счётчики и выбор точки.

### 1.3. Критические технические находки

- `Database` использует **одно** соединение SQLite и `RLock`; VFlow должен работать через те же методы/транзакции, а не открывать второе соединение в обход блокировки.
- `create_task_job()` сам строит `pipeline_json` из `task_successors` и при завершении задачи запускает детей. Для VFlow нужен отдельный путь постановки с пустым/контролируемым snapshot и явным запретом авто-fan-out.
- `create_task_job()` требует `tasks.is_published = 1` и `task_visible_to()`. Публикация VFlow может делегировать запуск внутренней задачи, поэтому нужен отдельный gateway-метод проверки: задача существует, разрешена опубликованной версией пайплайна и workspace инициатора, но не обязана быть видимой пользователю напрямую.
- `queue_jobs` не содержит ключа идемпотентности/происхождения VFlow. Нужны `pipeline_task_links` и/или поля корреляции (`vflow_run_id`, `vflow_point_id`, `origin_node_id`), иначе после рестарта нельзя надёжно связать задачу с точкой.
- `task_run_results` заполняется при `complete_task_run()`, но финальный ответ может быть недоступен (нет текста). Runtime должен различать «задача завершена, ответа нет» и «задача ещё выполняется».
- `tasks_only` ограничивает допустимые пути в `current_principal`; новые `/api/pipelines*` и `/api/pipeline-runs*` нужно добавить в allowlist, иначе пользователь `tasks_only` получит `403`.
- `task_successors` и `pipeline_json` — это **старая цепочка задач**, не VFlow. Имена таблиц/полей VFlow лучше выбрать с префиксом `vflow_` (или явно зафиксировать иное соглашение в ADR), чтобы не создать двусмысленность в коде и диагностике.

## 2. Целевая структура модуля

Предлагаемая структура (адаптировать под фактический репозиторий):

```text
src/opencode_web/vflow/
  __init__.py
  api.py              # пользовательские и административные HTTP-маршруты
  models.py           # dataclass/Pydantic/enums: IR, Run, Point, Fork, Arrival
  schema.py           # JSON Schema, IR-валидация, лимиты JSON
  parser.py           # VFlow -> AST с позициями
  compiler.py         # AST -> IR + семантическая/графовая валидация
  formatter.py        # IR -> канонический VFlow
  registry.py         # code-only реестр NodeSpec/Handler
  permissions.py      # аудитории, публикация, ownership, delegation
  repository.py       # SQLite-операции, CAS, транзакции
  runtime.py          # plan -> Action, переходы точки
  scheduler.py        # claim/lease/wake/recovery
  task_gateway.py     # адаптер к существующей очереди задач
  recovery.py         # рестарт, outbox, reconciliation
  events.py           # runtime events, audit, метрики
  blocks/
    base.py           # NodeHandler, NodeSpec, Action
    task.py           # valeria.task
    transform.py      # core.transform
    if.py             # core.if
    fork.py           # core.fork
    merge.py          # core.merge
src/opencode_web/static/vflow/
  editor.js           # SPA-модуль административного редактора
  pipelines.js        # пользовательская вкладка
  vflow.css           # стили на основе макета v2
```

HTTP-маршруты и таблицы — по §15 и §12 спецификации; конкретные имена зафиксировать ADR до начала кодирования.

## 3. Roadmap по этапам

| Этап | Результат | Эпики |
|---|---|---|
| A. Backend foundation | Версионируемый граф хранится в БД, компилируется и валидируется, но ещё не исполняется | A–E |
| B. Runtime MVP | Последовательные и параллельные графы исполняются, Task ставится в очередь, Fork/Merge/If/Transform работают, рестарт восстанавливает состояние | F–H |
| C. Пользовательская вкладка | Пользователь запускает опубликованные пайплайны и видит свои безопасные статусы | I–J |
| D. Административный редактор | Полноценный редактор на основе макета v2: палитра, canvas, инспектор, код, публикация, диагностика | I, K |
| E. Production hardening | Crash/fault injection, нагрузка, retention, наблюдаемость, документация | L |
| F. Extension SDK | Новые системные блоки добавляются только разработчиком через Registry и деплой | M |

## 6. Рекомендуемый первый вертикальный срез

Чтобы не строить весь модуль «вслепую», первым сделать сквозной сценарий:

```text
start -> Task(context.load) -> Transform -> If
                                      ├─ true  -> Task(report.approved) -> end
                                      └─ false -> Task(report.rejected) -> end
```

Порядок:

1. VF-A01–A03, VF-B01–B06 — ADR, таблицы, репозиторий.
2. VF-C01–C04, VF-D01–D08 — IR, Registry, минимальный DSL.
3. VF-E01–E04 — draft/validate/publish.
4. VF-F01–F05, VF-G01–G05 — scheduler, Transform/If, Task Gateway.
5. VF-I01–I07, VF-J01–J05 — пользовательский запуск.
6. VF-K01–K07 — редактор: палитра, canvas, инспектор, код, публикация.
7. Тесты EX-01–EX-06, VAL-01–VAL-07, UI-01–UI-05.

После этого добавить Fork/Merge, вложенность, recovery и live-диагностику.

## 7. Зафиксированные решения и оставшиеся вопросы

Зафиксировано 20.11.2026:

1. **Первый объём** — вертикальный срез `start → Task → Transform → If → Task → end`, затем Fork/Merge.
2. **Аудитория** — как у задач: `all`/`selected` пользователи + доступ для `tasks_only`; отдельные группы/подразделения не входят в MVP.
3. **Делегирование задач** — разрешено: опубликованная версия пайплайна может явно запускать внутреннюю задачу, не показывая её пользователю в каталоге.
4. **Public result** — в MVP только безопасные статусы; `public_result` и `public_output_schema` закладываются в модель, но UI результата не входит в первый срез.
5. **Редактор** — встраивается в текущий SPA-shell; трёхколоночный layout макета используется внутри общей оболочки VALERIA.

Осталось согласовать до соответствующих задач:

1. Может ли администратор запускать тестовый Run без workspace, или ему обязательно назначается workspace?
2. Стартовые лимиты: `max_fork_n=32`, 128 активных точек, 1 MiB JSON — оставляем рекомендованными или меняем?
3. Что делать с существующей цепочкой `task_successors`: оставить как отдельный legacy-функционал или постепенно заменить VFlow?
