## 1. Принципы выполнения

1. **Сначала P0-надёжность, потом новые возможности.** Не начинать Extension SDK и визуальные улучшения, пока не закрыты runtime, recovery и конфигурация.
2. **Один инкремент — один проверяемый результат.** Каждый инкремент заканчивается полным прогоном `tests/test_vflow_*.py`, `ruff` и `node --check`.
3. **Не ломать существующий VALERIA-функционал.** Изменения в `app.py`, `database.py` и `dispatcher.py` проверяются регрессионными тестами.
4. **Сначала контракт, потом реализация.** C03 (`NodeHandler.plan/Action`) должен быть готов до углубления G06/G07/H03.
5. **Frontend и backend параллелятся только при независимых файлах.** `runtime.py` — последовательная зона; `vflow.js` — тоже последовательная зона.
6. **Никаких коммитов без отдельного решения.** Текущая работа остаётся в рабочем дереве.

## 3. M0 — завершить J05

**Цель:** пользователь видит свои Run с фильтром по статусу и может подгружать историю порциями.

- API: `status`, `pipeline_id`, `limit`, `offset`; валидация статусов и границ.
- Runtime: параметризованный SQL без утечки внутренних полей.
- UI: фильтр, «Показать ещё», отсутствие дублей при polling.
- Тесты: фильтрация, пагинация, owner isolation, невалидный статус.

**Критерий готовности:** J05 закрыт, полный suite зелёный, в истории не появляются дубли, чужие Run по-прежнему `404`.

## 4. M1 — Runtime foundation

### 4.1. C03 — контракт `NodeHandler.plan/Action`

**Зачем:** сейчас runtime диспетчеризует типы узлов внутри себя. Нужен явный контракт, чтобы timeouts, recovery и новые блоки не разрастались в одном файле.

- Ввести `NodeHandler` с `plan(context) -> Action`.
- Ввести типизированные Action: `Advance`, `EnqueueTask`, `Suspend`, `SpawnFork`, `ArriveMerge`, `Finish`, `Fail`.
- Перенести Transform/If/Fork/Merge/Task на handler-и.
- Runtime применяет Action атомарно и остаётся единственным местом записи состояния.
- Тесты: handler не пишет в БД напрямую; неизвестный handler даёт безопасную ошибку.

**Зависимости:** нет. Делать первым в M1.

### 4.2. G07 — снимок Task на старте Run

- При `create_run` сохранять в `task_snapshots_json` параметры всех Task-узлов: task_id, title, queue, agent/model, версия/updated_at.
- Gateway при запуске использует snapshot, а не текущую запись Task.
- Изменение Task после старта Run не влияет на уже запущенный Run.
- Тесты: изменить Task после старта — Run продолжает работать по snapshot; новый Run видит новую версию.

**Зависимости:** C03 желателен, но можно делать параллельно после стабилизации модели Run.

### 4.3. G06 — таймауты и retry

- Разделить queue timeout и execution timeout.
- Не считать время в очереди временем выполнения.
- Retry только по явной настройке; каждый retry — новый attempt и новый Task Run.
- Ошибки: `TASK_TIMEOUT_QUEUE`, `TASK_TIMEOUT_EXECUTION`, `TASK_FAILED`; безопасные сообщения.
- Тесты: задача не стартовала до timeout; задача выполняется дольше execution timeout; retry создаёт ровно N Task Run.

**Зависимости:** C03, G07.

### 4.4. G04 — пробуждение по `job.updated`

- Добавить `wake()` в `VFlowScheduler` (idle-wait event).
- При событиях диспетчера `job.updated` будить scheduler, но сохранять polling как источник истины после рестарта.
- Не терять событие, если scheduler ещё не запущен.
- Тесты: ожидание Task завершается быстрее, чем при чистом polling; после пропущенного события Run всё равно продвигается.

**Зависимости:** C03.

### 4.5. A05 — конфигурация и feature flag

- Вынести лимиты и rate limit в `Settings`/`.env.example`.
- Добавить `VFLOW_ENABLED`; при выключенном флаге маршруты не регистрируются, UI скрывает разделы.
- Поддержать per-pipeline override лимитов через `settings_json` (fork N, points, transitions, JSON size).
- Валидировать значения при сохранении черновика.
- Тесты: feature flag, env override, невалидные значения, неизменность дефолтов.

**Зависимости:** C03/G06 для применения лимитов в runtime.

**Критерий M1:** EX-02/04/11, REC-07 и новые тесты snapshot/timeouts/wake/config зелёные.

## 5. M2 — Fork/Merge reliability

### 5.1. F08 — nested Fork/Merge и циклы

- Покрыть сценарии: Fork A → Fork B внутри ветки → Merge B → Merge A.
- Проверить `fork_stack`, порядок веток, запрет обхода Merge, повторный вход в Fork.
- Добавить тесты на цикл с Fork внутри и на лимит переходов.
- Исправить найденные расхождения в runtime/compiler.

### 5.2. H03 — crash recovery Fork/Merge

- Восстановление открытого Fork instance после падения между шагами.
- Восстановление Merge: все arrivals есть, но continuation не создан.
- Идемпотентный release: повторный recovery не создаёт вторую continuation.
- Тесты с имитацией падения на каждой границе транзакции.

### 5.3. H05 — диагностика аномалий

- RUNNING без активных точек.
- Открытый Fork без ожидаемых arrivals.
- Неизвестный handler/версия.
- Безопасные события и correlation id; без раскрытия prompt/JSON.

**Критерий M2:** REC-04/REC-05, EX-10/13/15/16 и fault-injection тесты зелёные; повторный recovery не создаёт дублей.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| SQLite lock при scheduler/recovery | короткие транзакции, `BEGIN IMMEDIATE`, никаких await внутри транзакции |
| Потеря события `job.updated` | polling остаётся источником истины; wake — оптимизация |
| Task изменилась во время Run | snapshot на старте Run, тест на изменение Task |
| Дубли Fork/Merge после рестарта | CAS + уникальные индексы + fault-injection |
| Legacy `task_successors` | VFlow всегда передаёт `pipeline_json=""` |
| Rate limit в нескольких процессах | вынести в общий store перед масштабированием |
| Расхождение UI и IR | graph ↔ code только через compile/format API |
