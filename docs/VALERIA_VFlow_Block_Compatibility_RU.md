# VFlow — политика совместимости и миграции блоков

**Статус:** действует для code-only Extension SDK
**Область:** `NodeSpec`, `NodeHandler`, Registry, опубликованные версии пайплайнов и активные Run
**Связанные документы:** `docs/VALERIA_VFlow_Extension_SDK_RU.md`, `docs/VALERIA_VFlow_ADR_RU.md` (ADR-004)

## 1. Инварианты

1. Каждый узел графа хранит стабильный `type` и точный `type_version`.
2. Registry адресуется парой `(type, version)`; компилятор отклоняет неизвестную пару с диагностикой `COMPILE_UNKNOWN_HANDLER_VERSION`.
3. Публикация версии фиксирует `required_handlers_json` и `graph_hash`. Активный Run ссылается на опубликованную версию и её IR, а не на «текущий» Registry.
4. Семантика уже выпущенной версии не меняется. Любое изменение поведения, формата конфигурации или портов требует новой версии (`custom.echo@1.1`, `core.transform@2.0`), а не правки `@1.0`.
5. Code-only: новый блок или версия попадают в систему только с релизом кода VALERIA и перезапуском/деплоем. Пользовательский плагин, загруженный JS/Python, `eval`, `exec`, импорт по имени, shell или SQL не являются частью SDK.

## 2. Закрепление версии handler-а

- Handler-версия закрепляется в момент компиляции: узел получает `type_version`, а версия пайплайна — `required_handlers_json` вида `["custom.echo@1.0", "core.transform@1.0"]`.
- Новый Run не подменяет handler и не «обновляется» автоматически. Он исполняет IR опубликованной версии.
- Новые версии пайплайна создаются отдельно. Старые опубликованные версии и их активные Run продолжают использовать закреплённый контракт.
- Registry должен содержать обработчик для каждой пары `type@version`, на которую ссылаются активные Run. Health-check сообщает о пропавших handler-ах как о деградации (`VFlowHealth`, проверка `handlers`), а не продолжает выполнение через заглушку.
- Нельзя удалять handler-версию, пока существуют активные Run или опубликованные версии, которые на неё ссылаются.

### Текущее ограничение dispatch

Реестр версионирован, но таблица выполнения `VFlowRuntime.handlers` в текущей реализации адресуется по `node.type`. Поэтому в одном деплое нельзя держать две несовместимые реализации одного `type` одновременно. Пока не появится version-aware dispatch, действует одно из правил:

- новая версия handler-а полностью совместима со всеми объявленными версиями этого `type`;
- несовместимое поведение выпускается под новым `type` (например, `custom.echo.v2`);
- старый handler остаётся в деплое до завершения зависимых Run, после чего замена выполняется отдельным релизом.

Это ограничение не отменяет version pinning в Registry, компиляторе, публикации и health-check.

## 3. Активные Run и вывод версии из эксплуатации

Порядок безопасного обновления:

1. Добавить новую версию `NodeSpec` и handler, не меняя старую.
2. Покрыть новую версию тестами конфигурации, Action-плана и выполнения.
3. Задеплоить релиз, в котором доступны и старая, и новая версии.
4. Убедиться, что health-check не показывает `missing_handlers` для активных Run.
5. Дождаться завершения Run на старой версии или выполнить явную процедуру их остановки/миграции по политике эксплуатации.
6. Только после этого отдельным релизом удалять старую версию.

Запрещено:

- заменять отсутствующий handler «пустым узлом», pass-through или иным неявным поведением;
- менять конфигурацию активного Run «на лету»;
- публиковать новую версию пайплайна, если её `required_handlers` отсутствуют в деплое;
- удалять тип блока, пока на него ссылаются опубликованные версии или активные Run.

## 4. Миграция конфигураций

В VFlow v1 нет автоматической миграции конфигураций узлов. Это осознанное ограничение: скрытая трансформация пользовательских данных усложняет аудит и может изменить смысл опубликованного пайплайна.

Правила:

- Старые Run читают ровно ту конфигурацию, которая сохранена в их IR.
- Новая версия блока с другим `config_schema` применяется только к новым узлам/новым версиям пайплайна.
- Если требуется перенос конфигурации, разработчик выпускает явную миграцию: новый `type@version`, документированное соответствие полей и отдельный тест на старые и новые данные.
- Администратор создаёт новую версию пайплайна и повторно сохраняет/проверяет узлы; старый опубликованный Run не переписывается.
- Миграция не должна выполняться в момент чтения активного Run.

## 5. Как добавить новый блок безопасно

1. Выбрать свободный `type` и версию; проверить отсутствие конфликтов call names.
2. Описать `config_schema`, входы, выходы, category/title и capabilities.
3. Реализовать handler, который читает только `PlanContext` и возвращает типизированный `Action`.
4. Зарегистрировать пару через `register_block(...)` в коде приложения/тестовой композиции.
5. Добавить DSL call names в `NodeSpec.call_names`; не менять парсер и общий UI.
6. Проверить манифест `/api/admin/vflow/block-registry`: type/version/title/category/config_schema/call_names/capabilities.
7. Написать тесты: регистрация, конфликты, компиляция source/IR, plan, capabilities, manifest, demo Run.
8. Проверить health-check и план отката.
9. Выпустить версию приложения и задеплоить; только после этого блок доступен администратору.

## 6. Чек-лист перед удалением или заменой блока

- [ ] Нет активных Run с `required_handlers`, содержащими удаляемую пару.
- [ ] Нет опубликованных версий пайплайнов, ссылающихся на неё.
- [ ] Health-check не показывает `missing_handlers`.
- [ ] Новая версия/тип задеплоены и проверены.
- [ ] Есть запись в аудите об изменении состава блоков.
- [ ] Документация и миграционная инструкция обновлены.
